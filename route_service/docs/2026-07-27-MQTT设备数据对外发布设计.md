# MQTT 设备数据对外发布设计

日期：2026-07-27
状态：原始版本已完成代码实现和真实链路验证；2026-07-28 确认由全量设备目录协议取代，变更设计见 `2026-07-28-MQTT全量设备目录对外发布变更设计.md`

> 本文保留原始在线目录设计和历史验收依据，不再作为软件部最终接入协议。最终交付必须以 2026-07-28 全量设备目录变更设计和更新后的接入说明为准。

## 1. 目标与范围

本设计定义 Route Service 向软件部系统提供设备信息和实时遥测的 MQTT 只读接口。软件部系统不连接 PostgreSQL，不依赖 Route Service 所在主机的文件或进程接口，只通过 MQTT 获得当前在线设备、设备基础信息、实时状态和最新遥测。

第一阶段目标如下：

- 软件部订阅一个固定 topic 后，立即获得全部在线设备的唯一标识符。
- 软件部根据设备唯一标识符订阅设备专属 topic，立即获得该设备的完整当前快照。
- 设备产生新遥测时，软件部继续从同一设备 topic 获得更新。
- 设备上线、离线、Route Service 重启或 MQTT 重连后，对外数据能够自动恢复到当前状态。
- 告警码随设备遥测原样发布，告警码含义通过接口文档附录提供。
- 软件部不需要读取数据库，也不需要理解 Route Service 内部表结构。

第一阶段明确不包含：

- 配置命令和飞控命令的对外开放；
- 历史遥测查询、回放和补发；
- 告警确认、告警消除和告警处置流程；
- 告警文字、颜色、图标、弹窗等界面展示规范；
- 面向软件部的数据库账号、数据表或 SQL 查询接口；
- 新增告警字典 MQTT topic。

## 2. 设计原则

### 2.1 MQTT 是软件部唯一数据接口

PostgreSQL 继续作为 Route Service 的持久化存储，但数据库边界不向软件部开放。Route Service 负责把数据库中已加载的设备资料和运行时收到的最新遥测组合成稳定的 MQTT 对外快照。

软件部只能依赖本文定义的 topic 和 JSON 字段，不得依赖数据库表名、字段名、Route Service 内存结构或日志格式。

### 2.2 使用 retained 快照实现“订阅后立即可见”

标准 MQTT 发布端通常不能感知某个客户端刚刚订阅了 topic，因此不设计“收到订阅动作后再查询数据库并回复”的特殊流程。

在线设备目录和单设备状态均使用 retained 消息。MQTT Broker 保存每个 topic 的最后一条完整快照，新客户端订阅后立即收到该快照，达到“订阅后立即看到数据”的效果。

### 2.3 发布当前状态，不承担历史存储

每个设备 topic 的 retained 消息只代表该设备当前最新状态。新遥测到达后，新快照覆盖旧快照。第一阶段不保证软件部断线期间每一帧遥测都可追溯，也不提供历史数据查询。

### 2.4 告警语义与展示解耦

Route Service 保留设备上报的原始告警字段和告警码，不负责把告警码翻译成人类可读文案。告警码、含义、触发条件和解除条件写入对外接口文档附录；软件部自行决定最终显示内容和交互形式。

## 3. 总体架构

```text
设备
  │ registration / telemetry
  ▼
Mosquitto
  │
  ▼
Route Service ────── PostgreSQL
  │                   仅 Route Service 访问
  │
  ├── retained 在线设备目录
  └── retained 单设备当前快照 + 后续实时更新
          │
          ▼
       Mosquitto
          │ 只读订阅
          ▼
      软件部系统
```

数据职责如下：

- 设备负责产生 registration、telemetry 和原始告警数据。
- Route Service 负责设备建档、在线状态判断、最新状态合并、数据库持久化和 MQTT 对外发布。
- Mosquitto 负责访问控制、QoS 交付和 retained 快照保存。
- 软件部负责订阅、解析、界面展示和自身业务状态管理。

## 4. Topic 设计

所有对外设备数据继续使用配置中的 `mqtt.topic_namespace`。以下示例以当前命名空间 `cns_rpi` 表示。

### 4.1 在线设备目录

```text
cns_rpi/events/devices/online
```

用途：

- 发布当前全部在线设备的 `vendor_id`；
- 帮助软件部发现设备并建立设备专属订阅；
- 设备在线集合发生变化时发布新的完整目录。

发布属性：

| 属性 | 值 |
|---|---|
| QoS | 1 |
| retain | true |
| 消息形式 | 完整快照 |

### 4.2 单设备当前状态

```text
cns_rpi/events/devices/{vendor_id}/state
```

示例：

```text
cns_rpi/events/devices/ABCDEF12345678901234/state
```

用途：

- 发布设备基础信息、在线状态和最新完整遥测；
- 新订阅者立即获得该设备当前快照；
- 后续遥测、上线和离线变化继续发布到同一 topic。

发布属性：

| 属性 | 值 |
|---|---|
| QoS | 1 |
| retain | true |
| 消息形式 | 完整快照 |

`vendor_id` 继续遵守现有约束：固定 20 个字符，只允许大小写英文字母和数字。

### 4.3 通配符订阅

软件部如需一次订阅所有设备状态，可使用：

```text
cns_rpi/events/devices/+/state
```

在线设备目录仍是判断当前有效在线设备集合的权威 MQTT 快照。通配符订阅可能收到已经离线设备的 retained 离线快照，软件部不得把“收到设备 topic”直接等同于“设备在线”。

## 5. 消息协议

### 5.1 在线设备目录消息

```json
{
  "schema_version": 1,
  "event_type": "online_device_snapshot",
  "generated_at": "2026-07-27T10:30:00.000Z",
  "revision": 18,
  "device_ids": [
    "ABCDEF12345678901234",
    "ZXCVBN12345678901234"
  ]
}
```

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | integer | 是 | 在线目录消息结构版本，第一版固定为 `1` |
| `event_type` | string | 是 | 固定为 `online_device_snapshot` |
| `generated_at` | string | 是 | Route Service 生成消息的 UTC RFC 3339 毫秒时间 |
| `revision` | integer | 是 | 在线设备集合版本，只在集合变化时递增 |
| `device_ids` | string[] | 是 | 当前在线设备唯一标识符，按字典序稳定排序 |

当没有在线设备时必须发布空数组：

```json
{
  "schema_version": 1,
  "event_type": "online_device_snapshot",
  "generated_at": "2026-07-27T10:30:00.000Z",
  "revision": 19,
  "device_ids": []
}
```

不得通过发布零长度 retained 消息删除在线目录，否则新订阅者将无法区分“当前没有在线设备”和“服务尚未发布目录”。

### 5.2 单设备当前状态消息

```json
{
  "schema_version": 1,
  "event_type": "device_state",
  "event_at": "2026-07-27T10:30:01.125Z",
  "revision": 1058,
  "vendor_id": "ABCDEF12345678901234",
  "school_id": 12,
  "school_name": "测试学校",
  "dcdw_label": "01",
  "model_version": "CNS v1.0",
  "status": "online",
  "last_seen_at": "2026-07-27T10:30:01.120Z",
  "telemetry_received_at": "2026-07-27T10:30:01.120Z",
  "latest_telemetry": {
    "latitude": 31.2304,
    "longitude": 121.4737,
    "altitude": 120.5,
    "speed": 14.2,
    "battery": 86,
    "alarm_codes": []
  },
  "change_reason": "telemetry",
  "degraded": false
}
```

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | integer | 是 | 设备状态消息结构版本，第一版固定为 `1` |
| `event_type` | string | 是 | 固定为 `device_state` |
| `event_at` | string | 是 | Route Service 生成本次消息的 UTC RFC 3339 毫秒时间 |
| `revision` | integer | 是 | 单设备单调递增版本，用于判断新旧和 QoS 1 去重 |
| `vendor_id` | string | 是 | 设备唯一标识符，与 topic 中的值必须一致 |
| `school_id` | integer | 是 | Route Service 内已建档的学校标识 |
| `school_name` | string | 是 | 设备所属学校名称 |
| `dcdw_label` | string/null | 是 | 设备角色号；未确定时为 `null` |
| `model_version` | string | 是 | 设备型号或协议模型版本 |
| `status` | string | 是 | `online` 或 `offline` |
| `last_seen_at` | string/null | 是 | 最后一次有效设备活动时间 |
| `telemetry_received_at` | string/null | 是 | 最新遥测被 Route Service 接收的时间 |
| `latest_telemetry` | object/null | 是 | 设备最新一份完整遥测；尚无遥测时为 `null` |
| `change_reason` | string | 是 | 产生本快照的原因 |
| `degraded` | boolean | 是 | Route Service 是否处于数据库写入降级状态 |

`change_reason` 使用现有枚举：

| 值 | 含义 |
|---|---|
| `registration_online` | 设备主动注册上线 |
| `registration_offline` | 设备主动注册离线 |
| `telemetry` | 收到新遥测 |
| `activity_timeout` | 设备活动超时，被判定离线 |
| `database_recovered` | 数据库恢复后重新同步 |

### 5.3 遥测透传约束

`latest_telemetry` 使用设备最近一次有效 telemetry 的完整 JSON 对象。Route Service 可以校验协议必需字段，但不得为了软件部展示而删除未知字段、重命名设备字段或把原始告警码替换为中文文案。

本设计只固定 `latest_telemetry` 外层封装，不在本文虚构设备遥测内部字段。遥测内部字段名、单位、量纲、精度、空值规则和告警编码由设备通信协议及其告警码附录定义。

如果将来需要调整遥测内部协议，应优先增加设备协议版本或新增兼容字段，不得静默改变已有字段语义。

## 6. 发布行为

### 6.1 Route Service 启动

Route Service 启动时按以下顺序处理：

1. 从 PostgreSQL 加载设备资料和最新状态。
2. 根据 `last_seen_at` 和 `offline_timeout_seconds` 重新计算设备是否仍在线，避免把数据库中的过期 `online` 状态对外发布。
3. 启动设备业务线程和 MQTT 客户端。
4. MQTT 连接及业务订阅成功后，发布一次完整在线设备目录。
5. 为每台当前在线设备发布一次完整设备状态快照。

软件部不需要等待设备产生下一帧遥测，即可在订阅后看到数据库中已保存的最新设备状态。

### 6.2 收到设备 registration

- 已知设备注册上线时，更新设备状态并发布该设备完整快照。
- 设备状态从离线变为在线时，更新并发布在线设备目录。
- 设备重复发送在线 registration、但在线集合没有变化时，不重复发布在线目录。
- 设备主动注册离线时，发布离线设备快照，并从在线目录移除。

### 6.3 收到设备 telemetry

- 校验 topic 中 `vendor_id` 与 payload 中设备身份一致。
- 更新设备的 `last_seen_at`、`telemetry_received_at` 和 `latest_telemetry`。
- 遥测可以使已知离线设备重新变为在线。
- 每份有效遥测产生一条新的完整设备状态消息。
- 只有设备由离线变为在线时才更新在线目录；普通遥测不重复发布在线目录。

### 6.4 活动超时

设备超过 `offline_timeout_seconds` 没有有效活动时：

1. Route Service 把设备状态更新为 `offline`。
2. 从在线设备目录移除该设备并发布新目录。
3. 向设备专属 topic 发布 retained 离线快照。
4. 离线快照保留最后一份 `latest_telemetry`，但软件部必须以 `status` 判断数据是否仍为实时状态。

### 6.5 MQTT 重连

MQTT 重连成功后，Route Service 必须重新发布：

1. 完整在线设备目录；
2. 所有当前在线设备的完整状态快照。

MQTT 连接回调不得直接并发读取或修改 `DeviceRegistry`。连接成功事件应投递到设备业务线程，由设备业务线程读取一致性快照并发起发布。

Broker 应启用持久化保存 retained 消息；Route Service 的重连全量发布仍需保留，用于修复 Broker 重启、数据丢失或运维清理后的状态。

## 7. 一致性与版本

### 7.1 在线目录版本

- Route Service 进程内维护在线目录 `revision`。
- 在线集合发生增加或删除时递增。
- 单纯遥测更新、基础信息未变化和重复 registration 不递增。
- Route Service 重启后允许从新的初始值重新开始；`generated_at` 用于跨进程实例判断时间。

软件部不得假设在线目录 `revision` 在 Route Service 重启后仍全局单调递增。

### 7.2 单设备版本

单设备消息使用 `DeviceRecord.revision`。同一 Route Service 运行和正常数据库恢复过程中，较大的 `revision` 代表较新的设备状态。

QoS 1 允许重复交付。软件部应使用至少以下组合去重：

```text
vendor_id + revision
```

如果软件部检测到较小 `revision`，应保留较新状态；Route Service 重启导致版本无法判断时，再结合 `event_at` 和新的 retained 快照恢复。

### 7.3 发布顺序

设备上线时，允许在线目录和设备状态消息在网络层先后到达。软件部在收到在线设备 ID 后订阅其状态 topic，Broker 会立即交付该设备 retained 快照，因此不依赖两个 topic 的跨 topic 严格顺序。

设备离线时，设备离线快照是判断单设备状态的最终依据；在线目录用于维护当前设备集合。

## 8. 告警码文档

第一阶段不新增以下 topic：

```text
cns_rpi/meta/alarm-codes
```

告警码映射作为对外接口文档附录交付。Route Service 只保证告警原始字段随 `latest_telemetry` 完整发布，不负责软件界面文案和样式。

告警码附录至少包含：

| 内容 | 要求 |
|---|---|
| 告警字段路径 | 明确告警位于 telemetry 的哪个字段 |
| 编码类型 | 字符串、整数、数组或位掩码 |
| 告警码 | 设备实际上传的稳定值 |
| 含义 | 对该告警的业务解释 |
| 触发条件 | 设备在什么情况下产生该码 |
| 解除条件 | 设备在什么情况下清除该码 |
| 组合规则 | 是否允许多个告警同时存在 |
| 无告警值 | 明确 `0`、空数组、`null` 等值的语义 |

如果设备使用位掩码，还必须说明：

- 数值采用十进制还是十六进制表达；
- 每一位的位序和含义；
- 保留位的处理方式；
- 多位同时置位时的组合方式。

软件部可根据该附录自行决定中文名称、颜色、图标、排序、声音和弹窗。遇到文档未定义的告警码时，软件部不得将其误判为“无告警”；应保留原始值，以便联合排查和补充协议文档。

## 9. MQTT 权限

为软件部建立独立只读 MQTT 账户。该账户只允许读取：

```text
cns_rpi/events/devices/online
cns_rpi/events/devices/+/state
```

该账户不得发布任何 topic，也不得读取以下设备原始入口和控制链路：

```text
cns_rpi/+/registration
cns_rpi/+/telemetry
cns_rpi/+/config/ack
cns_rpi/+/control/ack
cns_rpi/+/config/set
cns_rpi/+/control/set
cns_rpi/sources/#
```

Route Service 账户增加在线目录发布权限，并保留现有设备状态事件发布权限。

## 10. 异常与降级

### 10.1 数据库暂时不可用

Route Service 已经完成启动快照加载后，如果 PostgreSQL 暂时不可用：

- 继续处理设备 MQTT 消息；
- 继续从内存中的 `DeviceRegistry` 发布最新设备状态；
- 设备消息中设置 `degraded=true`；
- 数据库恢复后完成补写，并发布 `database_recovered` 状态；
- 软件部无需切换数据源。

如果 Route Service 启动时无法完成数据库快照加载，则按现有启动策略失败退出，不发布可能不完整的在线目录。

### 10.2 MQTT 暂时不可用

- Route Service 按现有重连策略恢复连接。
- 断线期间内存和数据库中的最新设备状态继续更新。
- 重连后重新发布当前完整快照。
- 第一阶段不补发断线期间每一帧历史遥测。

### 10.3 发布失败

- 单次发布失败必须记录中文诊断，但不得输出 MQTT 密码或完整敏感配置。
- 在线目录或设备状态发布失败后，连接恢复流程必须能够通过全量重发修复。
- 超过配置 `max_payload_bytes` 的设备原始消息继续按现有入口规则拒绝，不能发布被截断的遥测快照。

## 11. 性能与容量

- 在线目录只在设备集合变化、服务启动和 MQTT 重连时发布，不随普通遥测重复发布。
- 单设备 topic 按设备天然分流，软件部可按需订阅指定设备。
- 设备状态消息发布完整最新遥测，优先保证第一阶段接口简单和状态自包含。
- 第一阶段不引入遥测合并窗口、批量 topic、分页目录或历史队列。
- 如果后续设备数量或遥测频率明显增加，再根据实测吞吐增加可配置发布间隔或专用流式数据通道，但不得在未形成新协议版本前改变本设计语义。

## 12. 代码改造点

### 12.1 `core/device/device_registry`

增加只读在线设备快照接口，返回当前在线的 `DeviceRecord` 副本或等价稳定视图。结果按 `vendor_id` 排序，避免 `unordered_map` 遍历顺序导致在线目录无意义变化。

### 12.2 `core/mqtt_topic/device_topic`

增加在线目录 topic 构造函数：

```cpp
std::string OnlineDevicesTopic(std::string_view topic_namespace);
```

现有 `StateEventTopic` 继续生成：

```text
{namespace}/events/devices/{vendor_id}/state
```

### 12.3 `core/state_event/state_event`

在现有设备状态消息中补充：

- `revision`
- `school_id`
- `model_version`

继续保留 `latest_telemetry`、`change_reason` 和 `degraded`。

新增在线设备目录 JSON 构造函数，集中维护字段名、时间格式、排序和 schema version。

### 12.4 `adapters/mqtt/mqtt_client`

现有 `PublishStateEvent` 固定使用 QoS 0 且不 retain，不能满足新订阅者立即获得当前快照的要求。

发布接口应支持明确指定：

```text
QoS 1
retain true
```

在线目录和设备状态统一通过该接口发布。QoS 1 的完成回调、未知 MID 和重连生命周期继续遵守现有 MQTT 适配器约束。

### 12.5 `service_environment`

将现有 `RuntimeExternalBridge` 扩展或拆分为专门的设备对外发布器，负责：

- 构建设备状态消息；
- 维护在线设备集合和目录 revision；
- 只在在线集合变化时发布目录；
- 启动和 MQTT 重连后全量发布；
- 生命周期关闭后停止访问 MQTT 客户端。

连接回调只发送重发请求，不直接并发访问设备注册表。

### 12.6 配置与数据库

第一阶段固定使用 QoS 1 和 retained，不新增可关闭该行为的配置项，避免现场配置产生不兼容模式。

本设计不需要数据库迁移。

## 13. 测试要求

### 13.1 单元测试

- 在线目录 topic 生成正确。
- 设备状态 topic 保持兼容。
- 在线设备列表按 `vendor_id` 稳定排序。
- 无在线设备时生成空数组。
- 在线集合无变化时不产生新目录版本。
- 设备上线和离线时目录版本递增。
- 状态消息包含设备资料、revision 和完整 `latest_telemetry`。
- 原始告警字段不会在序列化过程中被删除或翻译。
- MQTT 发布参数为 QoS 1、retain true。

### 13.2 集成测试

使用本机 Mosquitto 验证：

1. Route Service 启动并发布在线目录。
2. 新客户端订阅在线目录后立即收到 retained 消息。
3. 客户端根据设备 ID 订阅设备状态后立即收到 retained 完整快照。
4. 新遥测到达后，同一 topic 收到更新。
5. 设备活动超时后，目录移除设备且设备 topic 收到离线快照。
6. 软件部客户端断开并重新连接后能够恢复当前状态。
7. Mosquitto 或 Route Service 重启后，当前目录和在线设备快照重新建立。
8. 软件部只读账户尝试发布时被 ACL 拒绝。
9. 数据库运行期暂时不可用时，设备状态继续发布且 `degraded=true`。

## 14. 验收标准

满足以下条件后，第一阶段可交付软件部：

- 软件部无需数据库账号即可获得当前在线设备 ID。
- 软件部订阅单设备 topic 后，无需等待下一帧遥测即可获得设备资料和最新遥测。
- 新遥测能够持续更新同一设备 topic。
- 设备上线和离线能够更新在线目录。
- 设备离线快照明确包含 `status=offline`，不会把历史遥测误表示为实时在线数据。
- Route Service 启动和 MQTT 重连后能够自动恢复全部当前快照。
- 软件部 MQTT 账户只有两个对外数据 topic 的读取权限。
- 对外接口文档包含完整遥测字段说明和告警码附录。
- 软件部不依赖数据库表结构、内部日志、控制 topic 或历史查询接口。

## 15. 后续扩展边界

控制命令、历史遥测和告警处置后续分别设计，不在本设计中预留未经确认的行为：

- 控制命令需要独立鉴权、幂等、ACK、超时和审计设计。
- 历史遥测需要独立查询接口或持久化流，不复用 retained 消息。
- 告警确认和处置需要状态机、责任人和审计记录，不等同于告警码展示。

后续扩展不得破坏本设计的两个只读 topic 和第一版 JSON 字段语义；如需不兼容修改，必须提升 `schema_version`。

## 16. 硬件服务器真实链路验收

2026-07-28 使用全新 MQTT 客户端完成只读订阅验证，客户端不连接 PostgreSQL，也不调用 backend_service：

```text
开发机 mosquitto_sub
  → 112.124.52.232:1883
  → 云端 frps
  → 硬件服务器 frpc.service
  → Mosquitto
  → Route Service 对外设备快照
```

验收结果：

- 首次同时订阅在线目录和单设备状态通配符时，立即收到 QoS 1、`retain=true` 的完整在线目录和全部已有设备状态；
- 在线目录只包含当前在线设备，离线设备保留 `status=offline` 的状态快照，验证了在线目录的权威语义；
- 在线设备快照包含学校、角色号、最后活跃时间、遥测接收时间以及完整的 `identity`、`drone_id`、`modules`、`telemetry`、`alarms` 和 `logs` 分组；
- 排除 retained 消息后，客户端连续收到新的 QoS 1、`retain=false` 状态消息，`revision` 连续递增且 `change_reason=telemetry`；
- 实时遥测包含姿态、双电池、5G、LoRa、电机、Remote ID、系统状态、模块状态、告警和日志等当前设备实际上报的数据；
- 验收期间客户端仅执行 MQTT 订阅，因此证明软件部无需数据库权限即可发现在线设备、恢复当前快照并持续接收实时遥测。

本次验收仍使用匿名明文 MQTT `1883`，只证明数据协议和公网转发链路可用，不代表 TLS、独立凭据和最小权限 ACL 已完成。
