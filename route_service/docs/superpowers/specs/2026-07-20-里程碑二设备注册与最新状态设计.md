# Route Service 里程碑二：设备注册与最新状态设计

版本：2026-07-20

状态：待书面审阅

## 1. 目标

本里程碑在里程碑一的 C++23 工程、PostgreSQL 迁移、MQTT 连接、有界队列和进程生命周期基础上，完成设备发现、设备建档、最新遥测、在线状态和规范化实时状态事件链路。

完成后，`route_service` 能够：

- 从 retained registration 发现设备并维护权威设备记录；
- 只保存每台设备的最新遥测，不保存逐帧历史；
- 使用服务器接收时间维护最后活跃时间；
- 通过显式 offline 和活动超时判断设备离线；
- 将实时状态事件与 PostgreSQL 合并写入异步分离；
- 在 PostgreSQL 运行中短暂不可用时继续维护已登记设备状态，并在恢复后补写；
- 为后续固定来源、配置命令和飞控命令里程碑提供可信设备目录。

V1 当前设备不足 10 台，采用全量内存设备目录。约 1,000 台以内预计无需改变本方案；达到更大规模时根据遥测大小、内存、启动时间和扫描耗时实测决定是否分页加载、分片扫描或拆分业务线程，不在本里程碑提前实现。

## 3. 总体架构

采用单业务线程、全量内存设备目录和单 PostgreSQL 工作线程：

```text
MQTT网络线程
  → topic形状与payload字节上限检查
  → 有界MQTT入站队列
  → 单业务线程
      ├─ topic与JSON协议校验
      ├─ 全量内存设备目录
      ├─ 在线状态机与离线扫描
      ├─ 规范化状态事件发布
      └─ 数据库期望状态提交
            → 单PostgreSQL工作线程
                ├─ 新设备建档事务
                ├─ 低频关键状态立即事务
                ├─ 遥测按设备合并写入
                └─ 断线重连与恢复补写
```

边界如下：

- MQTT 回调不解析 JSON、不查询数据库，只复制通过 topic 基本形状和大小检查的消息。
- 业务线程是内存设备目录和在线状态机的唯一修改者。
- PostgreSQL 工作线程独占同步 `libpqxx` 连接，业务线程不执行同步 SQL。
- 数据库任务不保存逐帧遥测队列。每台设备只保留最后一份期望持久化状态和脏字段，避免数据库故障期间内存随遥测帧数增长。
- 数据库结果通过内部结果队列返回业务线程；新设备只有在建档事务成功后才进入正式内存目录。
- 状态事件由业务线程基于完整内存快照生成，数据库写入不会阻塞实时事件。

不引入通用事件总线、ORM、连接池或为每个业务对象建立线程。

## 4. 启动、运行与停止

### 4.1 启动顺序

正常模式扩展为：

```text
解析命令行与严格配置
→ 连接PostgreSQL并检查迁移版本
→ 全量加载schools、devices、device_latest_states
→ 按last_seen_at修正已超时的online状态
→ 启动PostgreSQL工作线程
→ 启动业务线程
→ 启动MQTT网络循环
→ MQTT连接成功后订阅registration与telemetry
```

冷启动时 PostgreSQL 不可用仍按里程碑一规则启动失败，由 systemd 后续重试。服务不能在没有权威设备目录的情况下冷启动为降级模式。

数据库中仍为 `online` 的设备按保存的 `last_seen_at` 与当前服务器时间判断：未超过离线阈值时暂时保持 online，超过阈值时启动阶段立即转为 offline 并提交持久化，不重新开始 180 秒计时。

MQTT 首次连接或运行中重连成功后重新订阅。retained registration 按普通 registration 的幂等规则处理。

### 4.2 停止顺序

```text
停止接收新MQTT业务消息
→ 关闭MQTT入站队列
→ 业务线程处理完已入队消息
→ 请求PostgreSQL工作线程提交关键状态和最后合并快照
→ 到达有界等待上限后停止数据库线程
→ 停止MQTT网络循环并退出
```

停机排空不得无限等待，固定上限为 5 秒，不增加新的配置项。若 PostgreSQL 正处于故障状态，到达上限后记录未持久化设备数量并退出，不在日志中输出完整遥测 payload。

## 5. 配置扩展

在里程碑一严格 JSON 配置上新增：

```json
{
  "database": {
    "reconnect_interval_seconds": 5
  },
  "mqtt": {
    "topic_namespace": "cns_rpi",
    "max_payload_bytes": 262144
  },
  "device_state": {
    "telemetry_flush_interval_seconds": 5,
    "offline_timeout_seconds": 180
  }
}
```

规则如下：

- `database.reconnect_interval_seconds`：1～300 秒，示例值 5。
- `mqtt.topic_namespace`：必填非空字符串，只允许一个合法 MQTT topic 段，不允许 `/`、`+`、`#` 或空白。
- `mqtt.max_payload_bytes`：1,024～1,048,576 字节，示例值 262,144，即 256 KiB。
- `device_state.telemetry_flush_interval_seconds`：1～60 秒，示例值 5。
- `device_state.offline_timeout_seconds`：61～86,400 秒，示例值 180，并且必须大于 `mqtt.keepalive_seconds`。

离线扫描使用固定 1 秒业务节拍，不增加配置项。所有新增字段都是必填字段，不提供静默默认值；示例配置、解析测试、README 和设计文档必须同步。

## 6. MQTT topic 与接收边界

订阅：

```text
{topic_namespace}/+/registration
{topic_namespace}/+/telemetry
```

发布：

```text
{topic_namespace}/events/devices/{vendor_id}/state
```

业务 topic 必须具有准确层级，设备段必须符合 `vendor_id` 约束。含额外层级、空设备段、通配符字符或未知 suffix 的消息不进入业务处理。

MQTT 回调在复制 payload 前检查长度：

- 超过 `mqtt.max_payload_bytes` 时直接拒绝，不分配对应大块 JSON 缓冲。
- 入站队列已满时沿用“丢弃新消息”的 V1 规则，并限频记录严重错误。
- 日志只记录安全 topic、payload 字节数和拒绝原因，不记录完整外部 payload。

registration 订阅使用 QoS 2；telemetry 订阅使用 QoS 0。状态事件发布使用 QoS 0、`retain=false`。

## 7. Registration 协议与处理

### 7.1 Payload

Online：

```json
{
  "schema_version": 1,
  "vendor_id": "DCDWCNS1S2MEAG1VTA0C",
  "school_name": "SEU",
  "dcdw_label": "DCDW-001",
  "status": "online"
}
```

Offline：

```json
{
  "schema_version": 1,
  "vendor_id": "DCDWCNS1S2MEAG1VTA0C",
  "status": "offline"
}
```

校验规则：

- 根节点必须为 JSON object。
- 只接受 `schema_version=1`。
- `vendor_id` 必须存在、符合格式且与 topic 设备段一致。
- `status` 只允许 `online`、`offline`。
- online 必须包含非空字符串 `school_name`；`dcdw_label` 可省略，但存在时必须是非空字符串。
- offline 不要求学校和角色号。缺失字段表示本次不更新，不清空已有值。
- 已定义对象不接受错误类型；协议错误整条拒绝。
- 为兼容协议演进，根对象未知字段忽略，不进入稳定元数据列，但原始 registration 不单独持久化。

### 7.2 新设备

首次合法 online registration 生成一个待建档请求，由 PostgreSQL 工作线程在单事务中：

1. 按 `school_name` 创建或取得学校；
2. 创建 `devices`；
3. 创建 `device_latest_states`，状态为 online；
4. 创建对应的 `device` 类型 `command_sources`，`source_id=device_vendor_id=vendor_id`，默认启用。

事务成功后，业务线程才把设备加入正式内存目录并发布状态事件。事务完成前同设备重复 registration 合并为最后一份合法内容；telemetry 暂时拒绝并限频记录“设备建档尚未完成”。

事务失败时不产生部分设备记录。若失败表明 PostgreSQL 已不可用，本次新设备候选被移除，不在内存中接纳；确定性约束冲突记录错误并等待后续 registration。PostgreSQL 不可用时，不接纳从未登记过的新设备。数据库恢复后，route_service 对 registration 过滤器执行一次取消订阅和重新订阅，主动触发 Broker 重放 retained registration，再重新尝试发现仍在线的新设备。

### 7.3 已登记设备

- online registration 立即更新内存 online 状态和服务器接收的 `last_seen_at`。
- offline registration 立即更新为 offline，但不清空学校、角色号或最新遥测。
- registration 可以补充或更新 `dcdw_label`。
- 后续 `school_name` 与首次学校不一致时不自动迁校，保留原学校并记录错误；online 和活跃时间仍接受。
- `dcdw_label` 与同校其他设备冲突时只拒绝角色号更新；online 和活跃时间仍接受。
- 设备来源只在首次建档时自动创建。重复 registration 不得把管理员后续禁用的来源重新启用。
- QoS 2 重投、重连和 retained 重放允许产生语义重复消息，处理必须幂等。

## 8. Telemetry 协议与处理

树莓派当前 telemetry 没有 `schema_version`，各遥测分组按当前已收到的数据动态出现。route_service 采用最低必要校验，不解释 MAVLink 或传感器字段。

规则如下：

- 根节点必须为 JSON object。
- topic 设备必须已在正式内存目录中；未知设备和待建档设备的 telemetry 不得创建设备。
- `identity` 若存在必须为 object。
- `identity.vendor_id` 若存在，必须是字符串并与 topic 一致。
- `identity.dcdw_label` 若存在，必须是非空字符串，只在设备当前角色号为空时补全。
- telemetry 补角色号与同校其他设备冲突时，只拒绝角色号补全，仍接受遥测和活跃时间。
- 其余字段和未知字段不做业务校验，整份根 JSON 原样作为最新遥测快照保存。

每条合法 telemetry 使用 MQTT 回调收到消息后记录的服务器 UTC 系统时间作为 `last_seen_at` 和 `telemetry_received_at`。不使用数据库落库时间，也不尝试从设备 payload 推导真实产生时间。

合法 telemetry 立即：

1. 替换该设备内存中的最新完整遥测；
2. 更新最后活跃时间；
3. 若设备仅因活动超时离线，则恢复为 online；显式 offline 后收到合法实时 telemetry 也视为新的设备活动并恢复 online；
4. 发布完整规范化状态事件；
5. 标记该设备遥测为待合并持久化。

## 9. 在线状态机

状态转换：

```text
首次online registration → online
online registration      → online并刷新last_seen_at
合法telemetry            → online并刷新last_seen_at
显式offline              → offline
180秒无合法活动           → offline
offline后的新合法活动     → online
```

默认每 1 秒扫描内存设备目录。只有当前为 online 且 `当前服务器时间-last_seen_at >= offline_timeout` 时产生一次超时离线转换；已 offline 的设备不重复发布超时事件。

`offline_timeout_seconds` 必须大于 MQTT keepalive。当前 keepalive 为 60 秒、离线阈值为 180 秒，使 Broker 有足够时间触发 retained Last Will；超时扫描是遗嘱未及时到达、Broker/网络异常或状态遗漏时的兜底，不替代遗嘱。

显式 offline 和超时 offline 属于低频关键状态，立即提交数据库，不等待遥测刷新周期。

## 10. PostgreSQL 读写与一致性

### 10.1 启动加载

一次查询加载全部学校、设备和最新状态，并建立：

- `vendor_id → 设备状态` 索引；
- `school_id → school_name` 映射；
- `(school_id, dcdw_label) → vendor_id` 唯一性索引。

当前设计不分页。加载到不满足数据库约束或无法解析的记录时启动失败，不带着不完整权威目录继续运行。

里程碑一现有表结构已经覆盖本里程碑字段，预计不新增业务表或修改列。实施时仍需核对实际查询计划；若确需新增索引，只能追加新的版本化迁移，不得修改已经发布的 `002_创建核心业务表.sql`。

### 10.2 写入分类

立即写入：

- 新设备建档事务；
- registration 元数据变化；
- online/offline 状态转换；
- telemetry 导致的 offline→online 状态转换；
- telemetry 对空 `dcdw_label` 的合法补全。

合并写入：

- 持续 online 状态下的最新 telemetry、`last_seen_at` 和 `telemetry_received_at`，默认每 5 秒一次；
- 同一设备在周期内只写最后一份完整快照。

立即状态事务与合并遥测写入都采用参数化 SQL。JSON 使用 PostgreSQL JSONB 参数，不拼接 SQL 字符串。

### 10.3 运行中数据库故障

任一运行期数据库操作发现连接不可用后：

- PostgreSQL 工作线程进入断线状态，每 5 秒重新建立连接；
- 已登记设备继续由业务线程接收 registration 和 telemetry；
- 已登记设备立即更新内存并发布 `degraded=true` 事件；
- 每台设备只保留最后一份期望持久化状态，低频元数据按最终值合并，不保存无限任务历史；
- 未登记新设备不接纳；
- 本里程碑尚无命令，因此“数据库故障时停止命令”由后续命令里程碑实现。

重连成功后先重新校验迁移版本，再按设备补写最终状态，并重新订阅 registration 过滤器以重放故障期间拒绝的新设备 retained registration。补写成功的设备发布一次 `change_reason=database_recovered`、`degraded=false` 的完整状态事件。部分设备补写失败时只为成功设备解除 degraded；失败设备保留待写状态并继续重试。

数据库恢复不覆盖业务线程中更新得更晚的状态。每份待写状态带内存修订号；数据库结果返回时，业务线程只清除不晚于该修订号的脏标记。

## 11. 规范化实时状态事件

事件示例：

```json
{
  "schema_version": 1,
  "event_type": "device_state",
  "event_at": "2026-07-20T14:30:25.123Z",
  "vendor_id": "DCDWCNS1S2MEAG1VTA0C",
  "school_name": "SEU",
  "dcdw_label": "DCDW-001",
  "status": "online",
  "last_seen_at": "2026-07-20T14:30:25.123Z",
  "telemetry_received_at": "2026-07-20T14:30:25.123Z",
  "latest_telemetry": {},
  "change_reason": "telemetry",
  "degraded": false
}
```

字段规则：

- `schema_version`：固定整数 `1`。
- `event_type`：固定 `device_state`。
- `event_at`：本事件生成时间。
- `vendor_id`、`school_name`：始终为字符串。
- `dcdw_label`：尚未就绪时为 JSON `null`。
- `status`：`online` 或 `offline`。
- `last_seen_at`：尚无有效活动时为 `null`。
- `telemetry_received_at`：尚无遥测时为 `null`。
- `latest_telemetry`：尚无遥测时为 `null`，否则为设备最新完整 JSON object。
- `change_reason`：只允许 `registration_online`、`registration_offline`、`telemetry`、`activity_timeout`、`database_recovered`。
- `degraded`：PostgreSQL 连接是否已知不可用，或该设备是否仍有数据库故障期间积累且尚未补写成功的内容。正常 5 秒合并周期内尚未到刷新时间不算 degraded。

所有 JSON 时间由服务器生成，统一使用带毫秒的 UTC RFC 3339 `Z` 格式。数据库继续使用 `TIMESTAMPTZ`。

事件始终包含完整最新状态，不发布局部补丁。未来 backend_service 启动时先读 PostgreSQL 快照，再订阅本事件；按 `event_at` 处理快照之后的更新。状态事件不 retained，不能单独作为冷启动权威快照。

发布失败不阻塞数据库写入，也不重试 QoS 0 事件。记录限频警告，由 backend_service 断线后重新读取数据库快照恢复一致性。

## 12. 错误处理与日志

- topic 非法、payload 超限、JSON 语法错误、协议字段错误：拒绝消息并限频记录中文警告。
- 未知设备 telemetry：拒绝，不自动创建设备。
- 新设备建档约束冲突：事务回滚，不产生半条设备记录。
- 学校变化或角色号冲突：只拒绝冲突字段，保留其他合法状态变化。
- MQTT 入站队列满：丢弃新消息并限频记录严重错误。
- MQTT 断线：保持进程运行并自动重连；设备继续按离线阈值扫描。
- PostgreSQL 冷启动不可用：启动失败。
- PostgreSQL 运行中不可用：已登记设备降级运行，新设备拒绝，每 5 秒重连。
- 状态事件发布失败：不回滚内存或数据库状态。

日志不得包含数据库密码、MQTT 密码或完整 telemetry。允许记录安全 topic、`vendor_id`、字节数、错误码、数据库状态、待补写设备数量和截断后的异常字段上下文。

## 13. 代码边界

预计新增或扩展以下职责，不要求文件名与本节机械一致，但实现必须保持边界：

```text
src/core/mqtt_topic/          topic构造与严格解析纯逻辑
src/core/protocol/            registration、telemetry解析与校验
src/core/device/              内存设备目录、状态转换、离线扫描
src/core/state_event/         规范化事件构造与RFC 3339时间格式
src/core/persistence/         脏状态、修订号和合并策略纯逻辑
src/adapters/mqtt/            订阅、消息回调和发布
src/adapters/postgres/        全量加载、建档事务、状态upsert与重连
src/core/runtime/             业务线程、数据库线程和生命周期编排
```

纯协议、状态机和合并策略不依赖正在运行的 PostgreSQL 或 Mosquitto。外部库错误在适配层转换为带安全上下文的中文错误。

## 14. 测试与验证

### 14.1 本机单元测试

覆盖：

- topic 构造、准确层级、非法设备段和 namespace。
- payload 上限边界和入站队列满行为。
- registration online/offline、缺字段、错误类型、未知版本、topic/payload 身份不一致。
- 新设备建档请求、重复 registration 和局部 upsert。
- 学校不可迁移、角色号冲突只拒绝字段。
- telemetry 根类型、identity 类型、vendor_id 一致性、未知字段保留和角色号只补空。
- 未知设备与待建档设备 telemetry 拒绝。
- online、显式 offline、超时 offline、telemetry 恢复上线和不重复离线事件。
- 启动状态按保存的 `last_seen_at` 恢复，不重新开始计时。
- 默认 5 秒遥测合并、同设备只保留最后快照、多设备分别合并。
- 修订号防止旧数据库结果清除新脏状态。
- 数据库断线时已登记设备降级、新设备拒绝、恢复补写和部分成功。
- 状态事件完整字段、null 语义、change_reason、degraded 和 UTC 毫秒时间。
- 严格新增配置、数值范围和离线阈值大于 keepalive 的交叉校验。
- 敏感信息和完整 payload 不进入日志。

### 14.2 本机真实依赖联调

在本机 PostgreSQL 和独立 Mosquitto 测试端口上：

1. 重复执行迁移并正常启动 route_service；
2. 使用独立测试 `vendor_id` 发布 retained online registration；
3. 验证四张相关表和设备来源创建正确；
4. 发布多帧 telemetry，验证状态事件立即出现而数据库按周期只保存最后一帧；
5. 发布显式 offline，验证立即离线且不清空遥测；
6. 验证超时离线和后续 telemetry 恢复上线；
7. 暂停测试数据库连接条件，验证已登记设备发布 degraded 事件、未知设备不建档、恢复后补写；
8. 重启 route_service，验证 retained registration 恢复设备发现；
9. 验证 telemetry 实际为 QoS 0、非 retained，新订阅者不会收到旧遥测。

测试使用独立标识并定向清理自己创建的数据，不清空数据库，不影响其他项目数据。

### 14.3 树莓派联调

另一位同事完成设备端 telemetry `retain=false` 后，树莓派只向设备 registration 和 telemetry topic 发布。本里程碑验证 route_service 能接收真实 registration、真实 telemetry、角色号补全、显式/遗嘱 offline 和重新上线。

本里程碑没有命令路由。任何配置命令或飞控命令测试不得冒充已通过 route_service；完整配置命令链路最早在里程碑三验收。

### 14.4 现场验证

硬件服务器可用且用户另行授权后，服务器拉取对应提交再执行 PostgreSQL、Mosquitto、迁移和真实设备集成验证。服务器不可用时，本机结果不能写成现场已通过；验收记录必须明确列出延期项。

## 15. 验收标准

- retained registration 能幂等发现并事务化创建新设备。
- `vendor_id` 是权威设备主键，topic 与 payload 身份不一致时拒绝。
- 学校不自动迁移，角色号冲突不影响设备在线与遥测接收。
- telemetry 不创建设备，只保存每台设备最后一份完整 JSONB。
- 时间使用服务器接收时间，不使用落库时间或设备推导时间。
- 实时事件立即发布，遥测默认每 5 秒合并写库，两者异步分离。
- 显式 offline 和默认 180 秒无活动超时生效，新合法活动可恢复 online。
- PostgreSQL 冷启动不可用时退出；运行中不可用时已登记设备降级运行、未知设备拒绝、每 5 秒重连并恢复补写。
- 全量内存目录满足当前规模，设计未引入提前扩展复杂度。
- 状态事件为 QoS 0、非 retained，字段和时间格式符合本设计。
- 本机自动化测试和获授权的真实依赖验证通过；未执行的现场项明确记录。
- 未实现里程碑三命令功能，未修改 backend_service。
- `cns_rpi` 改动不在本里程碑提交范围，但联调验证 telemetry 非 retained。
