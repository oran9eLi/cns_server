# MQTT 发布完成 MID 误报修复设计

## 背景

route_service 使用同一个 libmosquitto 客户端发布配置命令、来源 ACK 和设备状态事件。libmosquitto 会为 QoS 0 状态事件触发发布完成回调，但当前适配层只登记配置命令和来源 ACK 的 MID，因此状态事件的 MID 被误判为未知或重复。设备持续上报遥测时，状态事件持续触发该误报，日志限流使其表现为每 30 秒输出一次。

真实联调已经确认状态事件正常到达 Broker，配置命令也完成了 `dispatched → applied → succeeded` 全链路，因此本修复只调整 MQTT 发布完成关联，不改变业务协议和状态机。

## 目标与边界

- 配置命令、来源 ACK 和状态事件的正常发布完成均不产生 MID 误报。
- 真正未登记或重复完成的 MID 仍输出原有限频错误。
- 消除来源 ACK 和状态事件在 `mosquitto_publish()` 返回与 MID 登记之间的快速回调竞态。
- 断线、停止和放弃回调时清理相关 MID。
- 不改变 MQTT topic、QoS、retain、payload、数据库结构、命令状态机或 ACK 协议。

## 设计

保留配置命令现有的 `token → MID` 与 `MID → token` 映射。将只服务于来源 ACK 的 MID 集合改为通用的“无需业务完成处理的 MID”集合，同时登记来源 ACK 和 QoS 0 状态事件。

所有需要分类发布完成回调的发布操作，都在回调状态互斥锁保护下完成 `mosquitto_publish()` 调用和 MID 登记。网络线程收到发布完成回调时若发布操作尚未释放锁，会等待登记完成，从而不会看到尚未来得及登记的 MID。

发布完成回调按以下顺序处理：

1. MID 属于配置命令：删除双向映射，并向命令服务提交一次完成结果。
2. MID 属于无需业务处理的发布：从集合删除并正常返回。
3. MID 不属于以上类别：按现有方式限频记录“MQTT收到未知或重复的发布完成MID”。

同一 MID 完成后即从登记结构删除，因此重复回调仍会进入第三种情况。连接断开、重新配置命令发布、放弃回调及客户端停止涉及的既有清理点同步清空该集合，防止旧连接状态污染后续连接。

## 容量与性能

配置命令容量限制继续只统计在途配置命令，不受状态事件影响。无需业务处理的 MID 集合只保存尚未完成的发布，完成后立即删除；在当前设备规模和 QoS 0 状态事件频率下，其大小由短暂的在途发布数量决定，不引入数据库或协议开销。

## 测试与验收

- 状态事件发布完成不记录未知 MID。
- 来源 ACK 发布完成不记录未知 MID。
- 配置命令完成仍只通知一次，并释放命令发布容量。
- 完全未知 MID 仍记录错误。
- 已完成 MID 再次回调仍记录重复错误。
- 断线后相关 MID 被清空，迟到回调按未知 MID 处理。
- 全量单元测试通过。
- 使用当前本机 Broker 和真实树莓派遥测观察至少 30 秒，不再出现周期性误报；服务器与 Broker 的启停由用户控制。
