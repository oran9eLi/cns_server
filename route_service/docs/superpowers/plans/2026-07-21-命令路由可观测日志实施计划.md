# 命令路由可观测日志实施计划

> **执行要求：** 使用 `superpowers:executing-plans` 逐项实施；本计划不使用子代理。步骤使用复选框跟踪。

**目标：** 为配置与飞控命令增加两类准确、简洁的 `INFO` 业务日志，展示可信来源、具体命令、学校与目标设备，以及设备应答的回程来源。

**架构：** 日志格式化和触发均位于 `CommandService`，复用其已解析的请求、可信 `ResolvedTarget`、设备 ACK 和持久化后的命令状态。新增独立 `InformationSink`，由运行环境接到现有 `Logger::Info`；错误仍使用既有 `DiagnosticSink`，日志异常不得影响命令状态机。

**技术栈：** C++23、nlohmann/json、doctest、现有异步 PostgreSQL 命令状态机与 MQTT QoS 2 发布接口。

## 全局约束

- 所有文档、代码注释、运行日志和提交说明正文使用中文；Git 提交前缀保持英文。
- 不修改 MQTT 协议、数据库结构、权限规则、ACK 内容或命令超时行为。
- 成功日志不得包含 `request_id`、`command_id`、原始 payload 或完整 MQTT topic。
- 设备显示格式为 `学校名 / 设备内部编号（vendor_id）`；字段缺失时使用设计文档规定的降级文本。
- 只有实际发布且成功持久化为 `dispatched` 的命令记录“已路由”；幂等状态回放不重复记录。
- 只有设备 ACK 状态成功持久化并已提交来源 ACK 发布后记录“已转发”。
- 实施前从 `main` 创建独立工作树，完成并验证后再按确认方式合回主分支。

- [ ] **步骤 1：声明并保存独立信息回调**

在头文件增加 `InformationSink`、末尾构造参数、`information_` 成员和 `Inform` 方法。保持默认空回调，避免测试或旧调用方必须提供日志器，也不改变现有位置参数含义。

- [ ] **步骤 2：实现可信设备显示**

在 `command_service.cpp` 匿名命名空间实现：

```cpp
std::string DescribeTarget(const command::ResolvedTarget& target) {
  const auto& school = target.school_name.empty() ? "未知学校" : target.school_name;
  const auto label = target.dcdw_label && !target.dcdw_label->empty()
                         ? *target.dcdw_label
                         : "未登记编号";
  return school + " / " + label + "（" + target.vendor_id + "）";
}
```

- [ ] **步骤 3：实现解析后命令显示**

配置请求只按固定协议字段顺序拼接已出现字段：

```text

mqtt_reconnect_delay_max_s
```

飞控请求使用 `set_motor_pwm`、`emergency_stop`、`takeoff`、`land`；仅 `set_motor_pwm` 追加 `pwm_us=[v1,v2,v3,v4]`。不得序列化原始 JSON。

- [ ] **步骤 4：实现异常隔离**

`Inform` 仿照 `Diagnose` 捕获所有异常：

```cpp
void CommandService::Inform(std::string message) noexcept {
  try {
    if (information_) information_(std::move(message));
  } catch (...) {
  }
}
```

### 任务 3：在持久化确认点接入两类日志

**文件：**

- 修改：`route_service/src/core/runtime/command_service.cpp`
- 修改：`route_service/src/service_environment.cpp`
- 测试：`route_service/tests/test_command_service_lifecycle.cpp`

**接口：**

- 使用任务 2 的 `InformationSink` 与 `Inform`。
- 运行环境把信息回调映射到 `RuntimeExternalBridge::Inform`，最终调用现有 `Logger::Info`。

- [ ] **步骤 1：在路由状态落库后记录**

处理 `OperationKind::kTransition` 的数据库结果时，仅当本次转换的期望结果是 `kDispatched` 且返回记录确为 `kDispatched`，使用上下文中的可信来源、解析后命令和目标记录输出：

```text
收到来自 <source_id> 的<配置命令或飞控命令> <命令描述>，已路由至设备 <学校 / 编号（vendor_id）>
```

不得在 `PublishRecord`、MQTT 发布回调刚成功或幂等查询回放路径记录。

- [ ] **步骤 2：在 ACK 状态落库和回程提交后记录**

对由设备 ACK 触发的 `kInProgress` 或终态转换，在 `PublishAck` 返回之后读取已解析并随上下文保存的业务状态，输出：

```text
收到来自设备 <学校 / 编号（vendor_id）> 的应答 <business_status>，已转发至 <source_id>
```

为避免把超时扫描、发布失败或恢复转换误判为设备应答，在 `RequestContext` 增加仅由合法且可关联设备 ACK 设置的可选业务状态；日志成功后清除此一次性标记，防止后续转换重复输出。

- [ ] **步骤 3：接入现有 INFO 日志器**

在 `service_environment.cpp` 构造 `CommandService` 时，于既有 `cleanup_batch_size` 实参之后新增：

```cpp
[weak = external](std::string message) {
  if (const auto bridge = weak.lock()) bridge->Inform(std::move(message));
}
```
