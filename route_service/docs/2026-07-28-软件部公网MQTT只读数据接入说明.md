# 软件部公网 MQTT 只读数据接入说明

## 1. 文档目的

本文面向仅通过 MQTT 获取 CNS 设备数据的软件系统。接入方无需访问 PostgreSQL，也无需调用 `backend_service`，即可完成：

- 发现当前在线设备；
- 获取所有已发布设备的最新状态快照；
- 持续接收在线设备的新遥测；
- 在客户端重启或网络重连后恢复当前状态。

本文只说明设备数据订阅，不包含配置命令、飞控命令、命令 ACK、数据库访问和历史遥测查询。

## 2. 当前公网接入参数

| 参数 | 当前值 |
|---|---|
| Broker 地址 | `112.124.52.232` |
| TCP 端口 | `1883` |
| MQTT 协议版本 | MQTT 3.1.1 |
| 用户名 | 当前不需要 |
| 密码 | 当前不需要 |
| TLS | 当前未启用 |
| 数据 QoS | `1` |

当前链路为：

```text
软件部客户端
  → 112.124.52.232:1883
  → 云服务器 frps
  → 硬件服务器 frpc
  → Mosquitto
  → Route Service
```

该入口已经使用全新 MQTT 客户端完成公网订阅验证。

当前 Broker 是匿名明文服务，协议用途虽为只读，但 Broker 暂未通过 ACL 强制限制客户端发布。接入方必须只订阅本文规定的两个 topic，不得向任何 CNS topic 发布消息。

## 3. 订阅 Topic

### 3.1 当前在线设备目录

```text
cns_rpi/events/devices/online
```

该 topic 发布当前所有在线设备的 `vendor_id` 完整集合。

| 属性 | 值 |
|---|---|
| QoS | `1` |
| retained | 是 |
| 数据形式 | 完整快照，不是增量 |
| 权威语义 | 判断当前哪些设备在线 |

Route Service 在以下时机发布在线目录：

- 服务启动并完成 MQTT 业务连接后；
- Route Service 与 Broker 断线重连后；
- 设备从离线变为在线时；
- 设备主动离线或活动超时离线时。

普通遥测不会导致在线目录重复发布。新客户端订阅后，Broker 会立即发送最近一份 retained 在线目录，因此不需要等待下一次设备上线或离线。

消息示例：

```json
{
  "schema_version": 1,
  "event_type": "online_device_snapshot",
  "generated_at": "2026-07-28T03:20:00.000Z",
  "revision": 5,
  "device_ids": [
    "DCDWCNS1S2MEAG1VTA0C"
  ]
}
```

没有在线设备时，`device_ids` 是空数组：

```json
{
  "schema_version": 1,
  "event_type": "online_device_snapshot",
  "generated_at": "2026-07-28T03:25:00.000Z",
  "revision": 6,
  "device_ids": []
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | integer | 消息结构版本，当前固定为 `1` |
| `event_type` | string | 固定为 `online_device_snapshot` |
| `generated_at` | string | Route Service 生成快照的 UTC RFC 3339 毫秒时间 |
| `revision` | integer | 本次 Route Service 进程内的在线集合版本 |
| `device_ids` | string[] | 当前在线设备的 `vendor_id`，按字典序排列 |

客户端每次收到该消息都应使用 `device_ids` **整体替换** 本地在线设备集合，不得把它当作新增设备列表。

### 3.2 所有设备当前状态

```text
cns_rpi/events/devices/+/state
```

`+` 代表单个 `vendor_id`。实际单设备 topic 示例：

```text
cns_rpi/events/devices/DCDWCNS1S2MEAG1VTA0C/state
```

| 属性 | 值 |
|---|---|
| QoS | `1` |
| retained | 是 |
| 数据形式 | 单设备完整当前快照，不是字段增量 |
| 更新时机 | 上线、离线、有效遥测和数据库恢复 |

通配符订阅可能立即收到在线设备和离线设备各自保留的 retained 状态。收到某个设备的状态 topic，不代表该设备当前在线；在线集合必须以 `cns_rpi/events/devices/online` 为准。

状态消息外层示例：

```json
{
  "schema_version": 1,
  "event_type": "device_state",
  "event_at": "2026-07-28T03:20:01.125Z",
  "revision": 590,
  "vendor_id": "DCDWCNS1S2MEAG1VTA0C",
  "school_id": 1,
  "school_name": "SEU",
  "dcdw_label": "DCDW-001",
  "model_version": "CNS v1.0",
  "status": "online",
  "last_seen_at": "2026-07-28T03:20:01.120Z",
  "telemetry_received_at": "2026-07-28T03:20:01.120Z",
  "latest_telemetry": {
    "identity": {},
    "drone_id": {},
    "modules": [],
    "telemetry": {},
    "alarms": [],
    "logs": []
  },
  "change_reason": "telemetry",
  "degraded": false
}
```

`latest_telemetry` 是设备最近一份有效遥测的完整 JSON，Route Service 不为展示端删除未知字段或重命名内部字段。当前真实设备遥测已经包含姿态、双电池、5G、LoRa、电机、Remote ID、系统状态、模块状态、告警和日志等数据；具体字段应以客户端实际收到的 JSON 和设备协议文档为准。

外层字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | integer | 消息结构版本，当前固定为 `1` |
| `event_type` | string | 固定为 `device_state` |
| `event_at` | string | Route Service 生成本次快照的 UTC RFC 3339 毫秒时间 |
| `revision` | integer | 当前 Route Service 运行期间的单设备状态版本 |
| `vendor_id` | string | 设备唯一标识，必须与 topic 中的值一致 |
| `school_id` | integer | Route Service 中的学校标识 |
| `school_name` | string | 学校名称 |
| `dcdw_label` | string/null | 校内设备编号；未确定时为 `null` |
| `model_version` | string | 设备型号或协议模型版本 |
| `status` | string | `online` 或 `offline` |
| `last_seen_at` | string/null | Route Service 最后收到有效设备活动的时间 |
| `telemetry_received_at` | string/null | Route Service 收到最新遥测的时间 |
| `latest_telemetry` | object/null | 最新一份完整遥测；尚无遥测时为 `null` |
| `change_reason` | string | 本次快照产生原因 |
| `degraded` | boolean | Route Service 是否处于数据库写入降级状态 |

`change_reason` 可能取值：

| 值 | 含义 |
|---|---|
| `registration_online` | 设备主动注册上线 |
| `registration_offline` | 设备主动注册离线 |
| `telemetry` | 收到有效遥测 |
| `activity_timeout` | 设备活动超时离线 |
| `database_recovered` | 数据库恢复后重新同步 |

设备离线快照仍会保留最后一份 `latest_telemetry`。此时这些数据只代表离线前的最后状态，不得作为当前实时值使用。

## 4. 命令行连通性验证

安装 Mosquitto 客户端后，可用一个进程同时订阅两个 topic：

```bash
mosquitto_sub \
  -h 112.124.52.232 \
  -p 1883 \
  -V mqttv311 \
  -q 1 \
  -i "software-read-本机唯一标识" \
  -v \
  -t 'cns_rpi/events/devices/online' \
  -t 'cns_rpi/events/devices/+/state'
```

`-v` 会同时打印 topic 和 JSON payload。连接成功后，即使设备此刻没有产生新遥测，也应立即收到 retained 在线目录和已有设备状态。

只观察连接后的新消息、不显示 retained 快照时，可执行：

```bash
mosquitto_sub \
  -h 112.124.52.232 \
  -p 1883 \
  -V mqttv311 \
  -q 1 \
  -i "software-live-本机唯一标识" \
  -R \
  -v \
  -t 'cns_rpi/events/devices/+/state'
```

不同客户端实例必须使用不同的 client ID。若两个连接使用相同 client ID，Broker 会断开其中一个连接，表现为客户端间歇掉线。

## 5. C/C++ 客户端接入要点

使用 Eclipse Paho MQTT C/C++、libmosquitto 或其他兼容 MQTT 3.1.1 的库均可。无论使用哪个库，都必须实现以下行为：

1. 为每个运行实例生成稳定且唯一的 client ID。
2. 连接 `112.124.52.232:1883`。
3. 在连接成功回调中订阅两个 topic，QoS 使用 `1`。
4. 网络断开后持续退避重连。
5. 每次重连成功后重新订阅，不能假定旧订阅仍然存在。
6. MQTT 回调只复制消息；JSON 解析和界面更新放到业务线程，避免阻塞 MQTT 网络循环。
7. 校验 `schema_version`，无法识别的主版本不得按旧结构静默解析。
8. 对单设备状态进行版本去重，并把每条消息当作完整快照覆盖本地状态。

使用 libmosquitto 时，核心调用关系如下：

```cpp
mosquitto_lib_init();

mosquitto* client =
    mosquitto_new("software-read-唯一实例标识", true, nullptr);

mosquitto_reconnect_delay_set(client, 1, 30, true);
mosquitto_connect_callback_set(client, OnConnect);
mosquitto_message_callback_set(client, OnMessage);

mosquitto_connect(client, "112.124.52.232", 1883, 30);
mosquitto_loop_forever(client, -1, 1);
```

连接成功回调中订阅：

```cpp
mosquitto_subscribe(
    client, nullptr, "cns_rpi/events/devices/online", 1);
mosquitto_subscribe(
    client, nullptr, "cns_rpi/events/devices/+/state", 1);
```

以上代码只展示接入骨架。生产代码还应检查每个函数的返回值、限制 payload 大小、捕获 JSON 解析异常并实现安全退出。

## 6. 客户端状态维护规则

建议维护两个相互独立的内存结构：

```text
online_device_ids: set<vendor_id>
device_states: map<vendor_id, 完整设备状态快照>
```

处理规则：

1. 收到在线目录后，完整替换 `online_device_ids`。
2. 收到设备状态后，以 `vendor_id` 更新 `device_states` 中对应的完整快照。
3. 界面是否显示设备在线，以设备是否存在于 `online_device_ids` 为准。
4. `device_states` 可以继续保留离线设备的最后状态，用于展示最后位置、最后遥测和离线前告警。
5. 不得依赖在线目录与单设备状态两个 topic 的跨 topic 到达顺序。

QoS 1 允许重复交付。单个 Route Service 运行期间，可使用以下组合去重：

```text
vendor_id + revision
```

同一设备收到重复或较小的 `revision` 时，不覆盖较新的本地状态。Route Service 重启后 `revision` 允许重新开始，因此客户端重连或识别到新服务实例数据时，应结合 retained 快照和 `event_at` 重新建立当前状态，不能把 `revision` 当作永久全局序号。

## 7. 断线、重连与异常处理

| 情况 | 客户端处理 |
|---|---|
| TCP 连接失败 | 采用退避策略持续重连，建议从 1 秒增长到最多 30 秒 |
| MQTT 连接断开 | 标记“数据连接不可用”，不要立即把所有设备判为离线 |
| 重连成功 | 重新订阅两个 topic，并用 retained 快照恢复状态 |
| JSON 无法解析 | 丢弃该条消息并记录 topic、错误类型和接收时间，不记录完整敏感 payload |
| 未识别的 `schema_version` | 拒绝按旧协议解释，记录协议不兼容 |
| 单设备消息重复 | 按 `vendor_id + revision` 去重 |
| 设备从在线目录移除 | 将设备显示为离线，保留其最后状态快照 |
| `degraded=true` | 数据仍可展示，同时提示服务端持久化处于降级状态 |

MQTT 客户端自身断线与设备离线是两个不同状态。客户端无法连接 Broker 时，只能说明数据链路不可用，不能据此断言所有设备都已离线。

## 8. 当前能力边界

当前 MQTT 只读接口提供设备发现和最新状态，不提供：

- 历史遥测查询；
- 遥测补发；
- 命令下发和命令 ACK；
- 告警确认、处置和审计；
- 数据库表或后端业务接口；
- Broker 端只读 ACL 保证。

客户端离线期间产生的中间遥测不会逐帧补发。重连后 retained 消息只恢复每台设备的最新状态。如果需要历史轨迹、统计分析或断线期间的逐帧数据，应另行设计历史存储和查询接口。

## 9. 接入验收标准

软件部客户端满足以下条件即可认为只读接入成功：

1. 能从目标运行环境建立到 `112.124.52.232:1883` 的 TCP/MQTT 连接。
2. 首次订阅后立即收到 retained 在线设备目录。
3. 能根据 `device_ids` 正确显示当前在线设备集合。
4. 首次订阅通配符后立即收到已有设备的 retained 状态。
5. 真实设备持续上报时，能连续收到 `change_reason=telemetry` 的新状态快照。
6. 能用 `vendor_id + revision` 处理 QoS 1 重复消息。
7. 设备离线后，能从在线集合移除设备，同时保留最后状态但不再视为实时数据。
8. MQTT 断开时显示“数据连接不可用”，而不是把所有设备误判为离线。
9. MQTT 重连后能够重新订阅，并通过 retained 消息自动恢复当前状态。
10. 客户端在整个验收过程中不向任何 CNS topic 发布消息。
