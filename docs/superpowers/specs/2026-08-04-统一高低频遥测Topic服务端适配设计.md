# 统一高低频遥测 Topic 服务端适配设计

> 状态：设计已确认，等待书面文档评审。本文只描述目标行为，不代表服务器当前已经切换 Topic。

## 1. 背景

`cns_rpi` 已在 `main` 分支实施统一高低频遥测发布通道。主控箱和 PX4 不再按设备类型使用不同的高频 Topic，而是按数据语义发布完整快照和实时帧：

```text
cns_rpi/{device_id}/telemetry/snapshot/v1
cns_rpi/{device_id}/telemetry/realtime/v1
```

服务器当前仍订阅以下旧 Topic：

```text
cns_rpi/{device_id}/telemetry
cns_rpi/{device_id}/px4/realtime/v1
```

因此新版 RPi 上线后，`route_service` 将收不到快照，`backend_service` 也收不到实时帧。本次迁移直接切换到新 Topic，不保留双订阅、双解析或旧协议兼容层。

## 2. 目标与非目标

### 2.1 目标

1. `route_service` 只消费 `telemetry/snapshot/v1`，沿用 schema v3 校验、最新状态维护和数据库写入逻辑。
2. `backend_service` 只在浏览器正在查看某台设备时，订阅该设备的 `telemetry/realtime/v1`。
3. 实时协议从 PX4 专用语义改为设备无关语义；主控箱电机字段和 PX4 飞行字段共用同一帧解析及 WebSocket 转发链路。
4. 浏览器端对主控箱和 PX4 都使用实时帧覆盖快照中的快变字段，断流时回退到最新快照。
5. 旧遥测 Topic 不订阅、不解析；测试明确锁定其废弃状态。
6. 同步服务器协议文档、部署文档和软件部公网 MQTT 只读接入说明。

### 2.2 非目标

- 不修改 RPi 帧结构和发布频率。
- 不将实时帧写入 PostgreSQL，也不建立实时历史记录。
- 不修改设备注册、命令、命令 ACK 或 PX4 真实 RTT Topic。
- 不在本次工作中实施 1000 台设备一小时容量压测；只保证实现满足按设备订阅和有界转发前提，压测单独执行。
- 不根据 `device_type` 维护两套实时 JSON 外壳或解析器。

## 3. 协议边界

### 3.1 快照通道

```text
Topic:  cns_rpi/{device_id}/telemetry/snapshot/v1
Schema: 3
QoS:    0
Retain: false
```

快照由 `route_service` 通配订阅：

```text
cns_rpi/+/telemetry/snapshot/v1
```

快照继续要求 Topic 中的 `device_id` 与 payload 顶层 `device_id` 一致。解析成功后更新内存设备状态、按既有节拍合并写入数据库，并发布规范化设备状态事件。`route_service` 不订阅实时通道。

### 3.2 实时通道

```text
Topic:  cns_rpi/{device_id}/telemetry/realtime/v1
Schema: 1
QoS:    0
Retain: false
```

实时帧顶层保持：

```json
{
  "schema_version": 1,
  "device_id": "DCDWCNS1S2MEAG1VTA0C",
  "sequence": 42,
  "sent_at": "2026-08-04T02:00:00.123Z",
  "telemetry": {}
}
```

`telemetry` 是开放对象：可以包含主控箱的 `motor`，也可以包含 PX4 的 `heartbeat`、`attitude`、`gps`、`global_position`、`sys_status`、`battery`、`pressure`。服务器只校验通用外壳和 Topic/payload 身份一致性，不依据设备类型拒绝已收到的字段。

### 3.3 继续保留的 PX4 专用通道

以下真实 RTT Topic 不变，仍只用于 PX4：

```text
cns_rpi/{device_id}/px4/latency/probe/v1
cns_rpi/{device_id}/px4/latency/ack/v1
```

### 3.4 废弃通道

```text
cns_rpi/{device_id}/telemetry
cns_rpi/{device_id}/px4/realtime/v1
```

服务器不为这两个 Topic 注册订阅，Topic 解析器也不接受其作为新遥测入口。由于 RPi 不双发，部署必须先完成服务器适配，再升级设备端。

## 4. 服务端架构

### 4.1 Route Service：只维护低频权威快照

`mqtt_topic::ParseDeviceTopic` 扩展为识别五段的 `{namespace}/{device_id}/telemetry/snapshot/v1`，`TelemetryFilter` 返回新快照过滤器。注册 Topic 仍保持三段结构。

Topic 解析不采用“任意后缀”匹配，只接受精确的 `registration` 和 `telemetry/snapshot/v1`。这样旧 `telemetry`、实时 Topic 以及拼写错误的版本号都会在接入边界被拒绝。

MQTT 订阅恢复、消息队列、schema v3 payload 解析、设备注册约束、状态事件和数据库写入流程均保持现状。该服务永远不接收 10～20 Hz 实时流，避免高频消息争用数据库和设备状态工作队列。

### 4.2 Backend Service：按页面兴趣动态订阅实时 Topic

后端 MQTT 网关启动时只常驻订阅：

- 规范化设备状态事件；
- PX4 RTT ACK；
- 配置和控制命令 ACK。

它不再常驻通配订阅全部实时帧。WebSocket Hub 维护全局 `device_id -> session count` 引用计数：

1. 某设备从 0 个浏览器订阅者变为 1 个时，通知 MQTT 网关订阅该设备的精确实时 Topic。
2. 同一设备增加更多浏览器会话时只增加计数，不重复向 Broker 订阅。
3. 会话显式退订、切换设备或断开连接时减少计数。
4. 计数从 1 变为 0 时，通知 MQTT 网关退订该设备 Topic。
5. MQTT 重连时，根据当前非零引用计数恢复精确订阅，不恢复已无人查看的设备。

动态订阅的目标集合是权威状态。订阅/退订回调失败时记录限频警告；连接恢复后按目标集合重新收敛。消息到达时仍校验 Topic 中的 `device_id` 与 payload 一致，不在目标集合内的迟到帧直接丢弃。

### 4.3 通用实时协议命名

服务器内部和浏览器协议移除 PX4 专用实时命名：

```text
Px4RealtimeFrame       -> DeviceRealtimeFrame
Px4RealtimeEvent       -> DeviceRealtimeEvent
px4.subscribe          -> telemetry.subscribe
px4.unsubscribe        -> telemetry.unsubscribe
px4.realtime           -> telemetry.realtime
broadcastPx4           -> broadcastTelemetry
```

这是服务器内部 WebSocket 协议的一次同步破坏性升级，不保留旧事件别名。PX4 RTT 的类型和事件名保持不变。

### 4.4 Frontend：通用快照回退与设备专用能力分层

前端拆分两类责任：

- `useDeviceRealtime`：对任意设备订阅 `telemetry.realtime`，在一个绘制周期内只保留最新帧，并把实时 `telemetry` 浅合并到快照遥测；超过 2 秒未收到实时帧时回退到快照。
- PX4 RTT 逻辑：只在 PX4 页面运行，继续发送探测并统计 RTT，不参与通用实时订阅。

主控箱详情页使用合并后的实时遥测刷新电机状态；PX4 控制台使用同一通用实时数据刷新飞行状态，并额外显示 PX4 RTT。界面文字使用“实时遥测/快照回退”，不再把通用高频链路称为“PX4 高频链路”。

浏览器 WebSocket 发送缓存超过现有限额时继续丢弃当前实时帧，不排队。该策略与 RPi 的“只发布当前最新状态”语义一致。

## 5. 数据流

### 5.1 快照

```text
RPi
  -> MQTT telemetry/snapshot/v1
  -> route_service schema v3 校验
  -> 内存最新状态
  -> PostgreSQL 合并写入
  -> retained 规范化设备状态
  -> backend_service
  -> 浏览器快照/断流回退
```

### 5.2 实时

```text
浏览器打开设备页
  -> WebSocket telemetry.subscribe
  -> WebSocket Hub 引用计数 0 -> 1
  -> backend_service 精确订阅设备 realtime/v1
  -> RPi 实时帧
  -> 通用外壳与 device_id 校验
  -> 仅转发给订阅该设备的浏览器
  -> 每个浏览器绘制周期只使用最新帧
```

页面关闭或切换设备时执行反向流程；最后一个浏览器离开后取消 Broker 订阅。

## 6. 异常处理

- 快照 Topic 非法、schema 不是 v3、Topic/payload 身份不一致：由 `route_service` 拒绝并按现有策略记录错误。
- 实时 JSON 非法、schema 不是 v1、Topic/payload 身份不一致：由 `backend_service` 丢弃并记录限频警告，不转发浏览器。
- MQTT 未连接：保留浏览器实时兴趣集合；连接恢复后重新订阅仍有人查看的设备。
- 浏览器异常断开：清理该会话全部设备兴趣并正确递减全局引用计数。
- 订阅与退订交错：以最终引用计数和目标集合为准，迟到回调不得恢复已取消的订阅。
- 实时断流：2 秒后停止使用实时帧并展示快照，不把设备直接判为离线；在线状态仍由 registration 决定。
- 慢消费者：后端 WebSocket 缓冲超过阈值时丢弃实时帧，前端一次绘制周期只应用最后一帧。

## 7. 测试设计

### 7.1 Route Service

- 精确解析 `cns_rpi/{device_id}/telemetry/snapshot/v1`。
- `TelemetryFilter` 生成 `cns_rpi/+/telemetry/snapshot/v1`。
- 拒绝旧 `telemetry`、旧 `px4/realtime/v1`、新 `telemetry/realtime/v1` 和错误版本。
- 新快照仍走 schema v3 解析、设备注册校验、状态更新和数据库脏标记流程。

### 7.2 Backend Service

- 实时 schema 接受含 `motor`、PX4 字段或两者并存的通用帧。
- 拒绝 schema 非 v1、Topic/payload 身份不一致及旧实时 Topic。
- 第一个页面触发一次精确 MQTT 订阅，后续同设备页面不重复订阅。
- 最后一个页面离开后触发一次退订；单个会话异常断开会清理其全部引用。
- MQTT 重连只恢复当前仍有浏览器兴趣的精确 Topic。
- 无人查看设备时，不订阅、不转发其实时流。
- 旧 PX4 RTT 探测和 ACK 测试继续通过。

### 7.3 Frontend

- 主控箱 `motor` 实时帧覆盖快照字段。
- PX4 动态字段通过同一通用实时事件更新。
- 2 秒无新帧后回退快照。
- 多帧在同一绘制周期到达时只渲染最后一帧。
- 页面进入、切换和卸载分别发送正确的通用订阅消息。
- PX4 RTT 仅在 PX4 控制台启用，主控箱不发 RTT 探测。

## 9. 部署与回滚

部署顺序：

1. 部署支持新快照 Topic 的 `route_service`。
2. 部署支持动态实时订阅的新 `backend_service` 和配套前端。
3. 验证服务器已经订阅快照新 Topic，浏览器进入设备页时才出现对应实时订阅。
4. 再升级 RPi；设备端不双发旧 Topic。
5. 分别验证主控箱电机实时刷新、PX4 飞行实时刷新、快照入库和 PX4 RTT。

回滚必须将服务器和 RPi 协议版本作为一组处理。只回滚服务器或只回滚 RPi 都会造成遥测 Topic 不匹配。数据库结构没有变化，不需要数据库备份或回滚迁移。

## 10. 验收标准

1. 新版 RPi 的快照持续更新设备最新状态并按现有策略入库。
2. 旧快照 Topic 和旧 PX4 实时 Topic 不会被服务器消费。
3. 主控箱详情页能从通用实时帧刷新四路电机状态；PX4 页面能刷新飞行动态字段。
4. 页面无人查看时，Backend 不订阅任何设备的通用实时 Topic。
5. 多个页面查看同一设备只产生一个 Broker 订阅，最后一个页面离开后退订。
6. 实时断流不影响快照显示、设备在线状态或命令链路。
7. Route Service、Backend、Frontend 全量单元测试、类型检查和构建通过。
8. 现场验证中数据库仅接收快照，实时帧不入库、不积压。
