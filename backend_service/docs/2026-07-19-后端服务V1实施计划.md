# Backend Service V1 全局实施计划

版本：2026-07-19

状态：全局路线已确认；各里程碑须另行完成设计、计划和验收

## 1. 目的

本文是 backend_service 与设备管理前端 V1 的全局实施路线，不是一次性连续执行的文件级任务清单。完整架构、协议、页面和部署边界见同目录 `2026-07-19-后端服务V1设计.md`。

V1 同时涉及 TypeScript 工程、PostgreSQL 只读模型、MQTT 实时事件、REST、WebSocket、React 页面、命令 ACK 和现场部署，必须拆成可独立验证、可独立合入 `main` 的里程碑。不得在一个功能分支中一次实现全部 V1，也不得在全局计划中提前锁定尚未进入的里程碑的文件级细节。

## 2. 固定开发流程

每个里程碑严格执行：

```text
确认前置里程碑及所需 route_service 契约已经合入 main
  → 在 main 阅读全局设计、全局计划和相关协议
  → 直接在 main 编写本里程碑设计文档
  → 用户逐节确认设计
  → 直接在 main 编写本里程碑详细实施计划
  → 用户确认详细实施计划
  → 从最新 main 建立隔离实施工作树
  → 按 TDD 分任务实现并频繁提交
  → 本机验证
  → 必要时经授权执行现场验证
  → 同步全部相关文档和验证记录
  → 完成里程碑验收并合入 main
  → 删除或归档实施工作树
```

只有前一里程碑完成验收并合入 `main`，才能在新的 `main` 编写下一里程碑设计与详细计划。文档确认前不建立实施工作树，不预先编写后续里程碑实现代码。

全局设计和全局计划放在 `backend_service/docs/`。每个里程碑使用“`YYYY-MM-DD-中文主题.md`”命名，分别放入：

```text
backend_service/docs/superpowers/specs/
backend_service/docs/superpowers/plans/
backend_service/docs/change_history/
```

里程碑设计和详细计划直接在 `main` 编写并提交；验证记录随实施工作树合入。前端属于同一 V1，前端相关设计、计划和验收记录也放在 backend_service 的上述文档目录，不另建一套流程。

## 3. 里程碑一：TypeScript 全栈工程基础

### 前置条件

Backend Service V1 全局设计和全局计划已经确认并进入 `main`。本里程碑不依赖 route_service 的业务实现完成。

### 目标

建立可安装、可构建、可测试、可配置的 TypeScript 全栈骨架和共享浏览器协议边界，为后续数据库、MQTT、WebSocket 和页面功能提供稳定工程基础。

### 范围

- 根目录 npm workspaces 和单一锁文件。
- `backend_service` 的 Node.js、TypeScript、Fastify 和测试工程。
- 顶层 `frontend` 的 React、Vite、TypeScript、Ant Design、TanStack Query 和测试工程。
- `shared/protocol` 的 REST/WebSocket 公共 schema 与类型边界。
- JSON 配置加载、Zod 校验、结构化中文日志和敏感字段保护。
- backend_service 进程生命周期、健康检查和有界资源配置骨架。
- 前端横向管理后台布局、设备列表页、设备详情页、路由、全局错误边界和 API/WebSocket 客户端接口骨架。
- 明确标注为开发用途的页面数据适配，使 route_service 尚未完成时也能在浏览器查看和评审完整页面；开发数据不得进入生产构建的默认路径。
- 本机不依赖 PostgreSQL、Mosquitto 和 route_service 的自动化测试。

### 不包含

- 真实数据库查询或 MQTT 连接。
- 真实设备列表、遥测或命令业务。
- Nginx、HTTPS、Basic Auth 和 systemd 现场部署。

### 完成条件

- 全量依赖可从干净环境通过锁文件重复安装。
- backend_service、frontend 和 shared protocol 构建通过。
- 单元测试、类型检查和静态检查通过。
- 健康检查与可查看的设备列表、详情和控制页面可在本机启动；页面使用开发数据时有明确标识，且不伪装为真实设备链路。
- 工程边界、开发命令和示例配置文档同步完成。
- 本里程碑代码、文档和验证记录合入 `main`。

## 4. 里程碑二：设备快照与实时只读管理页面

### 前置条件

- 里程碑一已验收并合入 `main`。
- route_service 的数据库基础、设备注册、最新状态和规范化实时状态事件已经验收并合入 `main`。
- backend_service 只读数据库角色及状态事件契约可以在本里程碑设计中基于已合入内容确定，不依赖另一工作树中的临时代码。

### 目标

完成“PostgreSQL 权威快照 + MQTT 实时增量 + REST/WebSocket 页面更新”的只读链路，交付可查看真实设备的管理页面。

### 范围

- PostgreSQL 独立只读账号所需权限与查询边界设计。
- `schools`、`devices` 和 `device_latest_states` 的只读查询。
- MQTT.js 连接和 `{namespace}/events/devices/+/state` 订阅。
- 先订阅、缓存事件、读取快照、按服务器时间戳合并的冷启动流程。
- `GET /api/devices`、`GET /api/devices/:vendor_id` 和运行期健康状态。
- 标准原生 WebSocket 会话、`session.ready`、Ping/Pong 和 `device.state` 广播。
- PostgreSQL、MQTT 和 WebSocket 断线后的只读降级与恢复。
- 设备列表页、筛选、独立详情页、核心遥测卡片和完整遥测视图。
- WebSocket 重连、REST 快照重取、旧事件不覆盖新值和降级提示。

### 不包含

- 配置或飞控命令提交。
- 命令 ACK、会话级结果路由和命令表单。
- 应用账号、JWT、学校隔离、审计和遥测历史图表。
- 公网正式部署。

### 完成条件

- 本机单元测试覆盖查询映射、协议校验、快照/事件合并、断线和资源上限。
- 前端测试覆盖设备列表、筛选、详情、字段缺失、实时更新和断线提示。
- 经用户授权后，在集成环境展示真实 PostgreSQL 设备快照和 MQTT 实时状态；未授权项明确记录为未验证。
- backend_service 的数据库权限经验证只有规定表的 `SELECT`，不能修改核心表。
- 本里程碑代码、文档和验证记录合入 `main`。

## 5. 里程碑三：配置与飞控命令桥接

### 前置条件

- 里程碑二已验收并合入 `main`。
- route_service 的固定来源、配置命令、飞控命令、来源 ACK、幂等、超时和恢复契约已经验收并合入 `main`。
- `web-console` 来源配置和可用学校范围已经在本里程碑设计中明确。

### 目标

完成浏览器 REST 命令提交、MQTT 来源请求、route_service/设备 ACK 和原浏览器 WebSocket 结果推送的真实端到端链路。

### 范围

- `POST /api/devices/:vendor_id/commands` 的配置和飞控判别联合协议。
- 浏览器 `client_request_id` 生成、重试复用和来源侧 `request_id` 映射。
- `session_id` 校验和 `request_id → session_id → WebSocket连接` 有界内存映射。
- `web-console` 固定来源的配置/飞控 request 发布和 ACK 订阅。
- MQTT QoS 2 发布回调的有界等待和 `202 Accepted` 语义。
- 本地快速校验、route_service 权威校验、幂等重试和冲突处理。
- `submitted`、`dispatched`、`in_progress`、终态及原始 `business_status` 映射。
- ACK 去重、终态延迟清理、断开会话和迟到 ACK 处理。
- 四项运行时配置表单。
- `set_motor_pwm`、`takeoff`、`land` 和 `emergency_stop` 控件。
- 命令按钮防重复提交、HTTP/MQTT/设备错误区分和 WebSocket 终态通知。

### 不包含

- 命令历史持久化或刷新后的命令状态恢复。
- 用户级权限、学校隔离和审计。
- 绕过 route_service 的设备直发能力。

### 完成条件

- 后端测试覆盖两类请求、参数边界、会话映射、QoS 2 发布结果、ACK 状态、幂等、超时、去重和清理。
- 前端测试覆盖全部配置和飞控请求、按钮状态及终态反馈。
- 相同 `client_request_id` 的相同请求不重复执行，冲突内容明确拒绝。
- 经用户授权后，两类真实命令均完成 route_service 与设备 ACK 端到端验证；飞控四类命令和配置四项参数的未验证项必须逐项记录。
- 本里程碑代码、文档和验证记录合入 `main`。

## 6. 里程碑四：安全入口、部署与综合验收

### 前置条件

- 里程碑三已验收并合入 `main`。
- route_service 已完成对应现场部署与综合验收，PostgreSQL、Mosquitto、数据库 schema 和 MQTT 契约处于可供 backend_service 使用的稳定状态。

### 目标

完成 Nginx、HTTPS、Basic Auth、systemd、故障恢复和 V1 现场综合验收，交付可通过授权入口访问的管理控制页面。

### 范围

- 现场 Node.js 活跃 LTS 版本验证和固定。
- `/etc/cns-server/backend-service.json`、专用服务账号、`0600` 权限和示例配置。
- backend_service 只监听 `127.0.0.1` 的 systemd 单实例、自动重启和资源限制。
- Nginx 静态前端、`/api/` 反向代理和 `/ws` WebSocket Upgrade。
- 公网入口 HTTPS 与 Basic Auth；若由穿透层终止 HTTPS，验证可信转发边界。
- PostgreSQL 冷启动失败、运行期断线、MQTT 断线重连、WebSocket 慢客户端和 backend_service 重启恢复。
- journald 结构化中文日志、敏感信息保护和非破坏性现场验证脚本。
- V1 全部验收项和恢复步骤记录。

### 不包含

- 修改 Mosquitto 为认证与 ACL 模式；该工作仍需独立安全设计、计划和授权。
- 应用账号、JWT、学校隔离和审计。
- 多实例、高可用、遥测历史和移动端专项适配。

### 完成条件

- 用户明确授权后才修改现场服务器、Nginx、systemd 或 HTTPS 状态。
- 无 Basic Auth 凭据时页面、REST 和 WebSocket 均被拒绝；公网凭据通过 HTTPS 传输。
- 真实设备列表、实时状态、四项配置和四类飞控命令完成综合验证。
- PostgreSQL、MQTT、WebSocket 和进程重启的故障恢复有实际证据。
- 服务器重启后 Nginx 与 backend_service 自动运行。
- 密码、证书私钥、真实配置和数据库数据未进入 Git。
- 全部自动化测试、现场验证记录和相关文档合入 `main`。

## 7. 全局验收边界

Backend Service V1 全部完成时必须满足：

- backend_service 只能读取规定的设备核心表，route_service 保持唯一写入者。
- 冷启动从 PostgreSQL 获得权威快照，实时状态只消费 route_service 规范化事件。
- REST 负责查询和命令提交，标准原生 WebSocket 负责实时状态和命令结果。
- `client_request_id` 直接作为来源 `request_id`，重试幂等和冲突检测生效。
- 配置与飞控命令全部经过 `web-console` 来源和 route_service，不直接控制设备 topic。
- 页面具备独立列表/详情、核心遥测与完整遥测视图、全部配置和飞控控件。
- WebSocket、PostgreSQL 和 MQTT 断线时行为明确，不出现静默伪成功。
- Basic Auth 只在 HTTPS 保护下用于公网入口。
- V1 不保存浏览器命令历史，不提供遥测历史、应用账号或多实例能力。
- 文档、代码注释、运行日志、提交正文和回答使用中文，协议标识保留英文。

## 8. 并行协作规则

route_service 和 backend_service 可以在不同工作树与功能分支并行开发。每个 backend_service 里程碑开始时必须从最新 `main` 建立工作树，并确认依赖的 route_service 里程碑已经合入；不得从 route_service 实施工作树直接复制或猜测尚未确认的契约。

如果 route_service 与本设计在 MQTT payload、状态枚举、数据库字段或部署配置上出现差异，先在 `main` 同步并确认所有相关设计文档，再继续对应里程碑实现。
