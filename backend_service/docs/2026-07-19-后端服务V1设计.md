# Backend Service V1 设计

版本：2026-07-19

状态：已逐节确认，书面规格已复核

2026-07-28 补充：Route Service 的设备数据 MQTT 输出已升级为 QoS 1 retained 在线目录与单设备当前快照，契约以 `route_service/docs/2026-07-27-MQTT设备数据对外发布设计.md` 为准。本文保留的 PostgreSQL 读取流程仅描述现有 backend_service V1；软件部若直接消费新 MQTT 接口，不需要数据库账号。

Route Service 里程碑三契约同步：backend_service 使用配置声明的固定 `source_id`，向 `{namespace}/sources/{source_id}/config/request` 发布 QoS 2、非 retained JSON。请求必须包含 `schema_version=1`、可稳定复用的 `request_id`、目标和配置参数；结果从对应 `/config/ack` 接收并按 `request_id` 关联。等待超时后必须复用原请求号重试，不得直接向设备 `/config/set` 发布。账号范围鉴权仍由 backend_service 后续里程碑实现。

## 1. 目标与范围

V1 以最快速度交付一个连接真实链路的基本设备管理控制页面。页面必须读取真实 PostgreSQL 设备数据、接收 route_service 的 MQTT 实时状态事件，并通过 route_service 对真实设备下发运行时配置和飞控命令。

V1 面向当前不足 10 台设备和少量内部浏览器会话，优先简单、可靠和便于嵌入式团队接手，不为多实例、高可用或大规模负载提前引入基础设施。

V1 包含：

- 设备列表、筛选和详情。
- 核心遥测卡片及完整遥测 JSON/键值视图。
- 全部四项运行时配置参数。
- `set_motor_pwm`、`takeoff`、`land` 和 `emergency_stop`。
- REST 查询和命令提交。
- 标准原生 WebSocket 实时状态与命令结果推送。
- Nginx Basic Auth、HTTPS 和 systemd 单机部署。

V1 不包含：

- 应用账号、JWT、学校数据隔离和操作审计。
- 命令历史展示或浏览器刷新后的命令状态恢复。
- 遥测历史、趋势图和 ECharts。
- 多实例、高可用、Redis、独立消息队列或大规模压力测试。
- 移动端专项适配。

## 2. 技术选型

### 2.1 已选方案

- 后端：Node.js、TypeScript、Fastify、MQTT.js、`pg`、Zod。
- 前端：React、Vite、TypeScript、Ant Design、TanStack Query。
- 实时通信：标准原生 WebSocket，不使用 Socket.IO。
- 包管理：npm workspaces 和根目录单一 `package-lock.json`。
- 反向代理与静态文件：Nginx。
- 进程管理：systemd。

TypeScript 贯穿前后端，使没有既有 Web 技术偏好的团队只需维护一种主要语言。Fastify 保持轻量，Zod 用于运行时协议校验并生成共享 TypeScript 类型。Ant Design 直接提供管理后台需要的表格、表单、状态、提示和布局组件。

WebSocket 用于服务端主动推送。命令仍通过 REST 提交，避免同时维护两套命令入口。与 SSE 相比，WebSocket 连接可直接代表浏览器会话，使命令 ACK 的会话级路由更直观。

### 2.2 未选方案

- Python/FastAPI：开发体验良好，但团队仍需维护前端 TypeScript，并额外处理 Python MQTT 回调、异步数据库和事件循环边界。
- Go：部署简单，但当前规模无法体现性能优势，首版协议与表单开发成本更高。
- Socket.IO：自动重连和房间功能并非 V1 必需，且会引入专有客户端与服务端协议。
- Zustand、Redux：V1 状态规模有限，TanStack Query、WebSocket 管理器和页面局部状态足够。

## 4. 与 route_service 的边界

route_service 是 `schools`、`devices`、`device_latest_states`、`command_sources` 和 `commands` 等核心表的唯一写入者。backend_service：

- 使用独立 PostgreSQL 账号，只获得 `schools`、`devices` 和 `device_latest_states` 的 `SELECT` 权限。
- 不读取 `commands` 作为 V1 页面数据源。
- 不执行数据库迁移，不拥有核心表的 `INSERT`、`UPDATE` 或 `DELETE` 权限。
- 不订阅设备原始 telemetry，不把它作为权威数据源。
- 订阅 route_service 发布的 QoS 1、retained 规范化当前状态快照。
- 固定使用 `source_id=web-console` 向 route_service 提交命令。
- 不直接发布设备 `config/set` 或 `control/set` topic。

现有 backend_service V1 仍从数据库建立其 REST 冷启动快照；面向软件部的新 MQTT 只读接口则以 retained 在线目录和设备状态恢复当前数据，不需要读取数据库。

启动同步采用“先订阅、后快照、再合并”：先订阅并缓存 MQTT 状态事件，再读取 PostgreSQL 快照，最后优先按 route_service 生成的 `event_at`，并结合 `telemetry_received_at`、`last_seen_at` 等服务器时间戳合并，旧数据不得覆盖新状态。

route_service 的在线目录 topic 为 `{namespace}/events/devices/online`，单设备状态 topic 为 `{namespace}/events/devices/{vendor_id}/state`，均使用 QoS 1 retained。设备状态 JSON 固定包含 `schema_version=1`、`event_type=device_state`、`event_at`、`revision`、`vendor_id`、`school_id`、`school_name`、`dcdw_label`、`model_version`、`status`、`last_seen_at`、`telemetry_received_at`、`latest_telemetry`、`change_reason` 和 `degraded`；三个可选状态字段缺失时显式为 `null`，时间使用 UTC 毫秒 RFC 3339 `Z`。`change_reason` 允许 `registration_online`、`registration_offline`、`telemetry`、`activity_timeout`、`database_recovered`。`degraded=true` 只表示 route_service 已知 PostgreSQL 不可用，或该设备仍有数据库故障期间积累且尚未补写的内容；正常 5 秒合并写入等待不算 degraded。详细对外契约以 `route_service/docs/2026-07-27-MQTT设备数据对外发布设计.md` 为准。

## 5. REST API

```text
GET  /api/health
GET  /api/devices
GET  /api/devices/:vendor_id
POST /api/devices/:vendor_id/commands
```

`GET /api/devices` 返回设备列表需要的 `vendor_id`、`school_name`、`dcdw_label`、`model_version`、`status`、`last_seen_at` 和 `telemetry_received_at`。V1 支持关键词、学校和在线状态筛选；当前设备量不做服务端分页，但响应使用 `{ "items": [...] }` 包装，为后续分页保留兼容空间。

`GET /api/devices/:vendor_id` 返回设备元数据、当前状态和完整 `latest_telemetry`。

配置与飞控命令统一提交到 `POST /api/devices/:vendor_id/commands`。浏览器不直接构造 MQTT target。配置示例：

```json
{
  "session_id": "当前WebSocket会话ID",
  "client_request_id": "浏览器生成的UUID",
  "type": "config",
  "parameters": {
    "telemetry_publish_interval_ms": 2000
  }
}
```

飞控示例：

```json
{
  "session_id": "当前WebSocket会话ID",
  "client_request_id": "浏览器生成的UUID",
  "type": "control",
  "command": "takeoff",
  "parameters": {}
}
```

`client_request_id` 在一次操作开始时由浏览器生成，并原样作为来源侧 MQTT `request_id`。网络重试复用原编号。相同编号、目标和内容表示幂等重试；相同编号但内容不同表示冲突。

成功受理返回 `202 Accepted`。backend_service 只在 MQTT.js 的 QoS 2 发布回调于配置的有界期限内成功完成后返回 202；这表示 Broker 已完成该次 QoS 2 交付握手，不表示 route_service 或设备已经执行成功。发布失败或等待超时返回可重试错误，前端重试必须复用原 `client_request_id`。错误统一为：

```json
{
  "error": {
    "code": "invalid_parameter",
    "message": "遥测上报周期超出允许范围"
  }
}
```

## 6. WebSocket 协议与会话

WebSocket 路径为 `/ws`。Nginx Basic Auth 同时保护 WebSocket 握手。建立连接后服务端先发送：

```json
{
  "type": "session.ready",
  "schema_version": 1,
  "session_id": "服务端随机会话ID",
  "server_time": "2026-07-19T00:00:00.000Z"
}
```

设备事件广播给全部连接：

```json
{
  "type": "device.state",
  "schema_version": 1,
  "vendor_id": "设备ID",
  "school_name": "SEU",
  "dcdw_label": "DCDW-001",
  "status": "online",
  "event_at": "2026-07-20T14:30:25.123Z",
  "last_seen_at": "...",
  "telemetry_received_at": "...",
  "latest_telemetry": {},
  "change_reason": "telemetry",
  "degraded": false
}
```

命令事件只发送给原提交会话：

```json
{
  "type": "command.updated",
  "schema_version": 1,
  "client_request_id": "浏览器请求号",
  "vendor_id": "设备ID",
  "command_type": "control",
  "status": "succeeded",
  "business_status": "accepted",
  "error": null
}
```

backend_service 维护 `request_id → session_id → WebSocket连接` 的有界内存映射。使用 Ping/Pong 清理失效连接。前端使用有上限的指数退避重连；重连后获得新 `session_id`，重新请求 REST 快照，不补发断线事件，也不恢复旧命令展示。

所有消息带 `schema_version` 和 `type`。前端忽略未知事件类型。设备状态按时间戳合并，旧事件不得覆盖新值。

## 7. MQTT 命令与状态处理

backend_service 订阅：

```text
{namespace}/sources/web-console/config/ack
{namespace}/sources/web-console/control/ack
{namespace}/events/devices/+/state
```

并发布：

```text
{namespace}/sources/web-console/config/request
{namespace}/sources/web-console/control/request
```

处理顺序：

1. 校验 `session_id` 对应 WebSocket 仍然连接。
2. 校验命令结构、字段类型、范围和组合约束。
3. 在发布前建立 `request_id → session_id` 映射。
4. 按 route_service 来源协议生成请求并以 QoS 2 发布。
5. MQTT.js 的 QoS 2 发布回调在有界期限内成功后返回 `202 Accepted`；失败或超时返回可重试错误。
6. 接收来源 ACK，更新内存状态并通过 WebSocket 推给原会话。
7. 终态后延迟清理映射，期间对重复 ACK 去重。

只有 MQTT 已连接且订阅就绪时才接受命令，否则返回 `503 mqtt_unavailable`。backend_service 可做快速输入校验，但 route_service 仍执行权威协议、来源、寻址、权限与幂等校验。

页面统一状态为：

```text
submitted → dispatched → in_progress → succeeded/failed/timeout/delivery_uncertain
```

来源 ACK 中 `applied`、`already_applied`、`accepted` 等原始状态保存在 `business_status`，不得被统一状态抹掉。backend_service 重启后映射丢失，迟到 ACK 只记录日志，不广播给其他会话。

## 8. 前端页面与交互

V1 路由为：

```text
/devices
/devices/:vendor_id
```

采用横向桌面管理后台布局。设备列表和设备详情为独立页面：

- 列表页显示设备总数、在线数、离线数、降级数和设备表格。
- 支持关键词、学校和在线状态筛选。
- WebSocket 事件直接更新对应设备，不整页刷新。
- 详情页左侧展示身份、状态、姿态、环境、链路、电机等核心卡片，以及完整键值/JSON 遥测。
- 遥测字段缺失时显示 `--`，不得构造伪造默认值。
- 详情页右侧展示运行时配置、飞控控制和当前命令状态。
- 同一设备存在未完成命令时禁用相关提交按钮；V1 不并行提交不同类型命令。
- HTTP 提交失败和 MQTT/设备执行失败分别展示。
- 命令终态使用 Ant Design notification 提示并保留当前命令详情。
- WebSocket 断开时持续告警并禁止命令提交；重连和快照同步完成后恢复。
- `degraded=true` 显示黄色“尚未持久化”提示，不自行判定设备故障。

TanStack Query 管理 REST 快照，WebSocket 管理器负责连接和事件分发，并把设备增量合并到 Query Cache。命令状态保存在详情页局部状态。V1 不引入 Zustand、Redux 或 ECharts。

## 9. 故障、一致性与资源边界

启动顺序为配置校验、PostgreSQL 连接、MQTT 连接与订阅、状态事件缓存、数据库快照、时间戳合并，最后才监听 HTTP/WebSocket。依赖未就绪时不暴露半初始化 API。

- PostgreSQL 冷启动不可用：启动失败并由 systemd 重试。
- PostgreSQL 运行期不可用：内存快照和 MQTT 实时事件继续工作；新的数据库查询返回 `503 database_unavailable`，服务定期探测恢复。
- MQTT 断开：REST 查询继续可用，WebSocket 广播降级，命令返回 `503 mqtt_unavailable`；重连并重新订阅后重新读取数据库快照。
- WebSocket 断开：不影响 REST；会话映射保留到终态或超时，但结果不转发给其他会话。
- route_service 拒绝或超时：保留原始错误码和安全中文信息，未知错误显示通用消息。
- 非法 HTTP、WebSocket、MQTT 或数据库 JSON：记录并丢弃单条异常数据，不使进程退出。

每个 WebSocket 连接使用有界发送缓冲。设备状态允许按 `vendor_id` 合并并只保留最新一份；命令结果不得静默丢弃，客户端持续无法消费时关闭连接。连接数、映射数、payload 大小、缓冲容量和清理期限均必须可配置并有安全默认值。

日志使用结构化 JSON 输出到 stdout/stderr，由 journald 保存。记录请求关联号、`request_id`、`vendor_id`、错误码和耗时；不记录凭据、密码、完整敏感配置、完整 telemetry 或完整命令 payload。

## 10. 构建、配置与部署

根目录 npm workspaces 提供统一的安装、构建、测试和开发命令。Node.js 使用现场验证通过的活跃 LTS 版本并固定版本范围。

前端构建为静态文件交给 Nginx。backend_service 只监听 `127.0.0.1`，由 systemd 以专用服务账号运行，不使用 PM2。Nginx 代理 `/api/` 和 `/ws`，正确设置 WebSocket Upgrade、连接超时和缓冲规则。

现场配置位于：

```text
/etc/cns-server/backend-service.json
```

配置包含 HTTP、PostgreSQL、MQTT、namespace、Client ID、固定 `source_id`、资源上限和日志等级。仓库只提交示例配置。现场文件归服务账户所有且权限为 `0600`，不得进入 Git。

Nginx 对页面、REST 和 WebSocket 统一启用 Basic Auth。Basic Auth 必须配合 HTTPS：可以由可信内网穿透层终止 HTTPS，也可以由 Nginx 终止；不得通过公网明文 HTTP 传输凭据。

正式 MQTT 接入已确认由 route_service 里程碑五统一提供端到端 TLS `8883`、用户名密码和 topic ACL。backend_service 使用独立 `web-console` MQTT 账户，只能发布自身 config/control request、读取自身 ACK 和规范化设备状态事件，不能直接向设备 set topic 发布。具体安全与部署边界见 `route_service/docs/2026-07-21-MQTT公网安全接入与FRP部署设计.md`。

## 11. 测试与验收

### 11.1 自动化测试

后端单元测试覆盖配置、协议校验、幂等冲突、会话映射、ACK 状态映射、快照与事件合并、断线、清理和慢客户端资源上限。

后端集成测试使用独立测试数据库和测试 Mosquitto，覆盖只读查询、三类订阅、两类命令发布、ACK 回程、MQTT 断线重连和数据库运行期故障。测试不得清空或修改现场已有数据。

前端测试覆盖列表筛选、实时状态、断线提示、遥测字段缺失、四项配置边界、四类飞控命令结构、按钮禁用、终态提示以及 REST/WebSocket 时间戳合并。

### 11.2 V1 验收标准

1. 无 Basic Auth 凭据时访问被拒绝，公网凭据通过 HTTPS 传输。
2. 页面展示真实 PostgreSQL 设备列表和详情。
3. 真实 telemetry 到达和设备上下线时页面无需刷新即可更新。
4. 四项运行时配置均可提交并显示 route_service 与设备 ACK。
5. `set_motor_pwm`、`takeoff`、`land` 和 `emergency_stop` 均可真实下发并显示最终结果。
6. 相同 `client_request_id` 重试不重复执行，冲突内容明确报错。
7. MQTT 断开时页面告警并禁止命令，恢复后可继续使用。
8. backend_service 重启后重新建立数据库快照和实时订阅。
9. Nginx 和 backend_service 在服务器重启后自动运行。

## 12. 开发与并行协作

设计文档和实施计划直接在 `main` 编写并提交。代码实现前，必须等待实施所依赖的 route_service MQTT、数据库和 ACK 契约进入最新 `main`，再从该提交创建 backend_service 独立工作树和功能分支。

route_service 与 backend_service 可以在不同工作树并行开发，但不得让 backend_service 根据另一工作树中尚未确认或尚未合入的临时代码反向猜测协议。发现跨服务契约差异时，先同步相关设计文档并确认，再修改实现。
